# Ozon 开店、账户与合规蒸馏

> 范围：只保留对 FBO 卖家和本项目有用的知识。具体费率、合同文本和受限品规则会变化，执行前应以卖家后台和官方当前页面为准。

## 1. 账户是所有数据的边界

- 一个 Seller 后台对应明确的法人/个体主体、结算信息、店铺和 API 权限。
- 本项目必须按 `shop_id` 隔离凭证、同步游标、业务事实和报表。
- Client-Id、Api-Key 只能本地加密保存，不写日志、不进 Git、不放前端。
- 使用 `/v1/roles` 做权限体检；缺少 Premium 或角色不应被解释为“没有业务数据”。

## 2. 合同与规则

经营中真正约束卖家的不是某个页面，而是以下规则组合：

- 卖家协议与平台规则；
- 类目准入和禁限售规则；
- 商品内容、品牌和知识产权规则；
- FBO 供应、包装、标签、验收规则；
- 退货、取消、赔付和争议规则；
- 佣金、物流、仓储及其他服务费；
- 促销、评价、沟通和违规处罚规则。

项目应保存“规则版本/生效日期/影响模块”，但不要把平台规则硬编码成永远不变的常量。

## 3. 商品合规

上架前至少判断：

- 类目是否允许销售；
- 是否需要证书、声明、注册或其他证明；
- 品牌是否需要授权；
- 商品名称、图片、描述是否侵犯权利；
- 包装、重量和尺寸是否符合要求；
- 标签、条码、有效期和序列化要求是否适用；
- 是否属于危险品、特殊储运、成人或其他限制类目。

证书不是“上传一次就结束”，应追踪：

- 证书类型和编号；
- 发证机构、有效期；
- 审核状态和拒绝原因；
- 已绑定商品；
- 到期提醒。

## 4. 数据与隐私

- 买家个人信息只能用于履约和法定用途。
- 不应把聊天、订单地址、电话等敏感字段无差别长期保存。
- 本项目当前是本地单机工具，这降低了外泄面，但仍要做最小采集、加密、备份和访问控制。
- 导出报表前应提供脱敏选项。

## 5. 运营合规的产品化

建议新增“店铺健康”检查：

- API 密钥有效性与权限；
- 证书即将到期；
- 商品被拒、隐藏、归档；
- 评级下滑；
- 退货/取消异常；
- 价格或库存异常；
- 财务同步不完整；
- 规则待确认。

## 6. 不应自动化的动作

以下动作即使有 API，也不能无确认执行：

- 删除商品或证书；
- 变更结算、账户或权限；
- 自动回复买家；
- 自动参加活动或大幅改价；
- 承认争议、赔付或放弃申诉。

## 7. 官方回放核验：从经营假设到开店

> 官方回放：[如何开始业务：卖家经验](https://www.youtube.com/watch?v=JjwYqZpnoLQ)，Ozon для партнёров，2023-09-21；官方时间轴核验日期：2026-08-03。

官方时间轴覆盖产品与创业路径、选择细分市场和商品、计算单位经济与风险、采购和供应商、选择履约模式、单据与主体形式、经营技能、团队、工具和问答。

可复用的开店顺序：

1. 明确商品、目标买家和差异化，而不是先批量上架。
2. 计算含商品成本、平台佣金、FBO 物流/仓储、推广、退货和税费的单位经济。
3. 核验供应商、证书、品牌权利、MOQ 和供货周期。
4. 选择法律主体、税制与单据链；税务判断由当前法规和专业会计确认。
5. 选择履约模式。本项目只采用 FBO，其他模式只保留比较知识。
6. 建立内容、供应、库存、售后、财务和复盘纪律，再扩大团队与规模。

视频中的 2023 年界面和产品名称不作为当前规则；其价值是经营决策顺序。

## 8. 官方卖家案例：转向 FBO 后仍需完整成本核算

> 官方来源：[艺术家卖家的 Ozon 经营经历](https://seller.ozon.ru/media/interviews/stranstvuyushij-hudozhnik-s-krasnym-diplomom-baumanki/)，核验日期：2026-08-03。

案例描述卖家在订单增长后转为 FBO，提前包装并按容器/仓库分配商品，由 Ozon 完成后续配送；同时强调质量、包装、库存纪律和财务核算。Ozon 分析只覆盖平台内部分费用，材料、包装、商品卡设计、人工等真实成本仍需卖家自行记录。

项目映射：

- 迁移到 FBO 是业务模式版本变更，保存开始日期、库存迁移和历史订单模式，不覆盖旧记录。
- FBO 省去逐单发运操作，不代表运营“自动完成”；供应计划、区域库存、包装、入仓、退货和对账仍需管理。
- 经营成本台账包含平台外成本与机会成本，利润不能从平台净到账倒推。
- 卖家案例属于经验材料，不用于证明平台硬规则或普遍经营收益。

## 9. 合同与公告的证据优先级

当官方材料冲突时按以下顺序处理：

1. 当前已接受的合同、附件和法律文件；
2. 当前专题知识库正文及卖家后台实际状态；
3. 明确生效日的官方变更公告；
4. 官方课程、视频和经营案例；
5. 第三方文章或经验。

项目保存 `source_type / version / published_at / effective_at / observed_at / superseded_at`。低级证据可以发现问题，但不能覆盖高级证据；任何合同、费率、税制和权限结论必须能回溯到当前来源。

公告把变更定位到具体合同附件和条款：每日、每周及提前付款的银行处理可能延续至计划日后 3 个工作日；每日/提前付款服务费在付款后的下一工作日扣除；Ozon 银行贷款有效期间，合同付款使用 Ozon 银行结算账户，结清后才能修改收款信息。

这是合同更新的标准处理示例：

- 公告发布日期不等于生效日，二者分别保存。

- 新合同版本上线前做影响分析，生效后以后台实际付款和单据验证；若不一致进入差异队列。

本项目不代替卖家接受合同，也不自动修改银行信息。合同接受、主体/账户变更及融资动作必须由有权限的人在官方后台完成。

## 11. 质量控制补充核验：商品真实性与证据

> 补充来源：[Ozon 质量控制体系说明](https://ozon-kontrol.tass.ru/)，核验日期：2026-08-03。该专题用于理解平台质量控制框架，不替代卖家合同、当前禁限售清单或 Ozon 大学专题正文。

材料说明平台会基于买家/权利人投诉要求卖家提供证书、许可或品牌权利文件；品牌权利人可通过品牌后台观察使用其品牌的商品并投诉疑似假货。常见问题包括商品型号、货号或商标与商品卡描述不一致，以及把受限商品放入错误类目规避限制。

项目约束：

- 商品合规证据按 `product × claim_type × document × valid_from/to` 保存，文件本身、适用商品/类目和审核状态分开。
- “正品/原装”属于需要证据的声明；平台标签、卖家提交文件与权利人授权均保留来源和有效期。
- 投诉不是违规结论。保存投诉、证据请求、卖家答复、平台决定、限制范围、申诉和恢复全过程。
- 类目错放不能只靠本地关键词判断；以平台类目、商品属性和官方限制规则为准。

## 12. 质量事件状态机

建议状态：

`signal → evidence_requested → evidence_submitted → under_review → cleared / restricted → appealed → restored / final`

每个事件保存：

- 商品、SKU、品牌、类目、店铺和受影响履约模式；
- 信号来源（买家、权利人、平台、监管或内部发现）；
- 规则/声明类型与当时版本；
- 请求和提交文件、截止日、审核人/系统决定；
- 隐藏、限售、冻结库存或账户限制的范围和起止时间；
- 申诉材料、结果与恢复验证。

系统可以提醒缺证、到期和答复截止日，但不得自动伪造证据、承认侵权、撤回申诉或规避平台限制。

## 13. 个人后台设置：控制面、权限与高风险变更

> 官方培训：[Ozon Seller 卖家后台导航](https://www.youtube.com/watch?v=e5Vmrt7g_Yo)，Ozon для партнёров，2023-12-08；官方时间轴核验日期：2026-08-03。
>
> 补充来源：[个人后台首页更新公告](https://seller.ozon.ru/media/news/lichnyj-kabinet-obnovili-glavnuyu-stranicu/)、[金融服务合同更新](https://seller.ozon.ru/media/news/o-finansovyh-uslugah-novoe-v-dogovore/)。知识库 `/libra/personal-account` 正文仍待浏览器逐页直读，因此具体角色名称、权限矩阵和当前菜单位置不在本节宣称为已核验规则。

官方培训把卖家后台定位为经营控制面，时间轴覆盖：后台设置、商品与价格、FBO、FBS、财务、分析、推广、卖家评级、评价、移动端和 Ozon 大学。对本项目而言，重要的不是复制 2023 年菜单，而是把账号配置与各业务域明确关联。

### 后台设置的业务边界

- **主体与合同**：公司/个体经营者资料、税务身份、合同版本和接受状态属于法律事实，变更必须保留历史版本。
- **收款与金融**：收款账户、付款频率、融资状态和服务费会影响现金流。官方合同公告说明，Ozon 银行贷款有效期间收款账户可能受合同限制，结清后方可修改。
- **成员与权限**：团队成员只能获得完成职责所需的最小权限。当前具体官方角色名待知识库正文核验，项目不固化第三方文章中的角色清单。
- **集成凭据**：Client ID、API 密钥和其他令牌是机器身份，不应与员工登录共享；按系统、环境和用途独立发放、轮换与撤销。
- **通知与沟通**：后台首页会汇总平台/买家沟通、服务指标、订单、销售与订阅信息，但历史公告中的布局不是当前界面保证。

### 项目权限模型

权限以能力域建模，而不是依赖页面菜单名称：

`catalog_read/write`、`price_read/write`、`fbo_supply_read/write`、`finance_read/export`、`analytics_read`、`promotion_read/write`、`feedback_read/respond`、`account_admin`、`credential_admin`。

高风险能力至少包括：账户/主体资料变更、收款信息变更、邀请或删除成员、权限提升、API 密钥创建/撤销、批量改价、参加促销、删除商品和提交供应。此类操作必须具备：

1. 明确操作者和授权来源；
2. 操作前差异预览与二次确认；
3. 不可篡改的审计记录；
4. 失败/部分成功结果；
5. 可行时的撤销或人工恢复说明。

### 安全工作流

- 入职：验证工作邮箱与身份，按岗位授予最小权限，禁止多人共用账号。
- 调岗：先撤销旧职责权限，再授予新权限；保留变更人、原因和生效时间。
- 离职/外包结束：立即撤销后台、API、导出文件和本地工具访问；轮换可能接触过的密钥。
- 定期复核：至少按人员、能力域、最后使用时间和高风险操作重新确认访问需求。
- 密钥泄露：立即撤销并新建最小权限密钥，检查调用与数据导出日志，不把密钥写入 Markdown、截图、仓库或日志。

本项目当前只读同步与分析能力可默认开放给运营角色；任何写入 Ozon 的能力都应单独授权。FBS/realFBS 菜单即使存在，也不进入项目可操作权限集合。

## 14. 品牌后台：权利主体、商品监控与投诉证据链

> Ozon 大学入口：`/libra/account-brand`；课程目录另含“Ozon 品牌”课程。
>
> 官方补充来源：[Ozon 质量控制体系说明](https://ozon-kontrol.tass.ru/)，核验日期：2026-08-03。知识库正文和课程内容仍待逐页直读；本节只采用官方专题能够直接支持的事实，不把未核验的申请条件、时限或当前按钮写成规则。

品牌后台面向权利人，不等于普通店铺装修或商品卡里的品牌字段。官方材料说明，权利人可用它观察其他卖家销售其品牌的商品，并对疑似假货发起投诉。投诉之后，平台可能向卖家索取证书、许可或品牌文件；卖家不能在规定期限内提供时，商品卡可能被限制。

### 必须分开的主体与关系

- **品牌（brand）**：名称、标准化写法、适用类目和平台标识；
- **权利人（rights holder）**：拥有商标、著作权或其他权利的法律主体；
- **申请/授权主体**：在平台提交材料的人，可能是权利人、被许可人或代理人；
- **卖家与商品**：实际销售该品牌商品的店铺、offer、SKU 与商品卡；
- **权利文件**：商标证书、许可/经销链、授权书、采购与进口来源等，各自有范围和有效期；
- **平台状态**：品牌后台资格、商品“原创/正品”标记、投诉和平台决定是不同事实，不能互相替代。

### 投诉与审核流程

建议状态机：

`observed → suspected → complaint_submitted → evidence_requested → evidence_submitted → under_review → dismissed / restricted → appealed → restored / final`

每个案件至少保存：

- 品牌、权利类型、权利人及其平台身份；
- 被投诉店铺、商品卡、SKU、截图和发现时间；
- 投诉理由：疑似假货、未经授权销售、盗用图片、商标/型号/货号不一致等；
- 平台案件号、提交时间、证据截止日和当时规则版本；
- 双方证据原件、文件校验值、适用地域/类目/商品和有效期；
- 平台决定、限制范围、申诉、恢复与最终验证。

投诉是风险信号，不是侵权事实；品牌权利也不能从商品卡上的品牌文字自动推断。平台“原创/正品”标记只代表平台所述的附加核验状态，不能替代本地保存的权利链和商品来源证据。

### FBO 与项目约束

- FBO 入仓前把品牌授权、商品真实性、强制标记和质量文件设为 SKU 级前置检查；一旦商品卡被限制，库存仍可能在仓，必须继续跟踪取回、解限或处置。
- 商品来源证据与品牌权利证据分开：合法采购不必然授予商标管理权，拥有商标也不自动证明每一批货物来源。
- 项目可以汇总疑似侵权、缺证和截止日，但不得自动提交投诉、承认侵权、伪造授权或绕过平台限制。
- 当前申请门槛、保证金、“原创”标记条件、处理时限和可投诉范围必须在实际操作前核对 Ozon 大学当前正文和合同。

## 15. 珠宝销售：高价值商品、许可文件与 FBO 单据

> Ozon 大学入口：`/libra/jewerly`（官方路径保留该拼写）。
>
> 已核验官方依据：[Ozon 质量控制体系](https://ozon-kontrol.tass.ru/) 与 `/libra/finances-documents/electronic-documents/edo` EDI 正文；核验日期：2026-08-03。珠宝知识库正文仍待逐页直读，当前准入主体、国家监管登记、标签字段、仓点和退货规则不得从本节静态推断。

官方质量材料把珠宝列为对质量敏感、需要在销售前提交相应许可文件的类目之一；已核验的 EDI 正文则把珠宝 FBO 供应列入必须使用电子单据的场景。由此可确定：珠宝不是普通商品卡增加几个属性，而是“主体资格—商品唯一性—质量/权利文件—FBO 供应单据—高价值售后”的完整控制链。

### 商品与合规事实

每个珠宝 SKU 至少预留：

- 品类与材质：贵金属、宝石/镶嵌物、成色、重量、尺寸等平台要求属性；
- 制造商、品牌、供应商、原产国和采购批次；
- 商品级或批次级唯一标识、吊牌/封签及监管标识（具体字段以当前官方正文为准）；
- 许可、证书、声明、品牌授权和来源文件的号码、签发方、适用范围、有效期及原件；
- 商品卡、实物、标签和单据之间的型号/货号/材质一致性检查。

缺少当前正文时，项目不得自行判断某件饰品是否法律上属于珠宝，也不得凭商品名称自动绕过珠宝控制。

### FBO 供应与 EDI

- 珠宝供货在已核验 EDI 页面中属于强制电子单据场景；供应前检查 EDI 连接、签名、供货 УПД-2、卖家/收货方和商品行一致性。
- 供应批次关联每件商品/批次标识、箱/封签、单据、仓点和验收结果；高价值商品不应只按汇总数量入库。
- 仓库接收资格、包装、防拆、运输和交接要求必须按珠宝正文及当期仓点核对。
- FBO 验收差异保留开箱/封签、件数、重量、唯一标识和 EDI 回执证据。

### 售后与补偿

- 退货时比对唯一标识、封签、材质/重量、配件和证书，区分原件、调包、缺件、损坏和正常可售退货。
- 买家退款、商品返仓、质量检查、可售状态、平台责任和补偿分别记录。
- 高价值补偿保存估值来源、采购/制造成本、单据、商品状态和平台决定；标价不自动等于补偿基数。
- 任何销毁、取回、重新上架或证书替换都属于高风险人工确认动作。

### 项目边界

当前项目默认不启用珠宝专项操作。只有确认经营相关 SKU，并完成当前 Ozon 大学正文、合同和适用法规核验后，才开放珠宝合规检查；否则只识别并提示风险。

## 16. Ozon Select：精选渠道资格与品牌证据

> Ozon 大学入口：`/libra/ozon-select`。
>
> 当前官方产品依据：[Ozon Select 官方应用页面](https://apps.apple.com/ru/app/ozon-select-%D0%B1%D1%80%D0%B5%D0%BD%D0%B4%D0%BE%D0%B2%D1%8B%D0%B5-%D1%82%D0%BE%D0%B2%D0%B0%D1%80%D1%8B/id6745216294)，开发者为 OZON.ru；补充依据：[Ozon 质量控制体系](https://ozon-kontrol.tass.ru/)。核验日期：2026-08-03。卖家申请条件、类目、国家、费用、流量权益和审核时限仍需 Ozon 大学正文/后台核对。

官方产品说明把 Ozon Select 描述为精选品牌商品体验，重点强调限定/稀缺系列、品牌原装商品、权利人或官方代表供货，以及经过审核的卖家。因此 Select 应被建模为附加的渠道资格与商品纳入状态，而不是新的履约模式。

### 四层资格

1. **卖家资格**：法律主体、店铺、服务质量与平台审核状态；
2. **品牌资格**：权利人、官方代表或授权链及其适用范围；
3. **商品资格**：具体 offer/SKU 是否被 Select 接纳、拒绝、暂停或移出；
4. **持续资格**：证据有效期、投诉、退货/质量信号和平台复核。

必须保存 `select_program_id / seller_status / brand_status / offer_status / decision_at / reason_codes / evidence_ids / valid_from/to / source_checked_at`。店铺通过不代表全部商品自动进入；商品在主站可售也不代表 Select 可售。

### 商品与品牌一致性

- 商品卡品牌、型号、货号、原产信息和实物/包装必须与权利及来源文件一致。
- 权利人、官方经销/代理、普通合法转售是不同关系；只有当前规则认可的关系才能支持相应资格。
- “Select”“原创/正品”及品牌后台资格是不同平台状态，不得互相推导。
- 限定/独家系列需要额外保存系列、销售地域、期限和授权范围，营销文案不能超出证据。

### 运营与项目边界

- Select 订单仍按其真实履约模式处理；本项目只允许 FBO 操作，不创建所谓 `select_fulfillment`。
- 渠道曝光、转化、退货和净利润可用 `sales_channel=ozon_select` 分析，但订单、库存和财务事实仍与主站稳定 ID 对齐并防重复。
- 资格申请、品牌声明、提交授权、接受额外条款和申诉均为高风险人工动作。
- 若官方正文不可读取，项目只展示“资格未知/待核验”，不得凭品牌知名度或第三方文章自动标记为可加入。

## 17. 官方卖家案例：品牌注册与团队建设

> 官方来源：[注册品牌并添加到 Ozon](https://www.youtube.com/watch?v=CfCceLdTRM0)、[从单干到团队](https://www.youtube.com/watch?v=50WGvt5fK00)，Ozon для партнёров；官方 RSS 标题与描述核验日期：2026-08-03。两条均被官方描述为卖家经验/启发，不是统一法律或平台操作规范。

品牌案例能证明“构思品牌—取得外部权利—在 Ozon 添加品牌”是多个阶段，而不是一次后台点击。项目应分别记录：

- 品牌名称与商品卡使用状态；
- 商标申请、注册、权利人、类别、地域、有效期和官方登记证据；
- 授权/代理链、适用商品与期限；
- Ozon 品牌添加申请、材料、决定、拒绝原因和复核；
- 品牌后台、Ozon Select、原创品牌保证金等后续资格，禁止相互自动推导。

团队案例支持随着经营扩张从单人处理转向职责分工，但不证明任何固定组织结构。结合个人后台控制面，项目采用：

- 以职责分配最小权限，商品、FBO 供应、财务、推广和高风险设置分域授权；
- 邀请、接受、角色调整、临时授权、停用和离职撤权形成成员生命周期；
- 品牌声明、合同、收款账户、商品卡/库存迁移、融资和删除类操作要求双重确认或人工复核；
- 共享账号、共享验证码和无法追责的批量操作均不作为可接受协作方式。

案例中的成功路径和团队规模不可视为普遍结果；当前商标法律程序、平台材料和具体角色权限仍需运行时核对。
