# Ozon FBO 履约、供应与库存蒸馏

> 项目唯一履约模式：FBO。FBS、rFBS、FBP 不建设。

## 1. FBO 的业务本质

卖家把货供应到 Ozon 仓。Ozon 负责主要仓储、分拣和配送。卖家仍需负责：

- 需求预测和备货；
- 供应单、货件和运输安排；
- 包装、条码、标签和合规；
- 入仓差异跟踪；
- 仓间库存结构；
- 滞销和长期仓储；
- 退货、报损、补偿和财务核对。

## 2. 供应生命周期

建议项目按事件保存，而不是只保存最终状态：

1. 创建供应草稿；
2. 选择入仓方向/仓库；
3. 提交 SKU 与数量；
4. 获得供应单；
5. 创建货件/货位；
6. 生成标签和交接文档；
7. 发运；
8. 到仓；
9. 验收；
10. 上架；
11. 产生差异、拒收或补偿；
12. 转为可售库存。

核心对象：

- `supply_order`
- `cargo/cargo_place`
- `carriage`
- `warehouse`
- `product/sku`
- `expected_qty`
- `accepted_qty`
- `available_qty`
- `damaged_or_rejected_qty`

## 3. 入仓差异

不能只比较“发了多少”和“现在库存多少”。应分别保存：

- 计划数量；
- 实际发运；
- 到仓扫描；
- 验收；
- 拒收/差异；
- 上架；
- 调拨；
- 已销售；
- 退货回仓；
- 报损和补偿。

推荐对账式：

`期初可售 + 验收入库 + 退货回仓 + 调拨入 - 销售出库 - 调拨出 - 报损/处置 = 期末库存`

允许存在时间差，但必须能解释。

## 4. FBO 库存不是一个数

经营至少要看：

- 可售；
- 预留；
- 在途；
- 待验收；
- 不可售/残次；
- 退货处理中；
- 按 Ozon 仓或集群的分布；
- 最近销量、可售天数和缺货天数。

## 5. 补货

基础补货逻辑：

`目标库存 = 预测日销量 ×（采购周期 + 运输入仓周期 + 安全天数）`

`建议补货 = 目标库存 - 可售 - 在途 - 待验收`

还应考虑：

- 活动带来的需求抬升；
- 季节性；
- 仓库覆盖和跨区配送；
- 最小采购量和整箱；
- 资金占用；
- 长期仓储风险；
- 入仓容量和时间窗口。

## 6. 库存风险分层

- 缺货：可售为 0 且近期有销量；
- 临界：可售天数低于完整补货周期；
- 健康：覆盖目标区间；
- 过量：明显高于目标；
- 滞销：长时间无销量；
- 长仓风险：接近平台长期仓储计费条件；
- 数据风险：库存同步不完整或标识无法映射。

## 7. FBO 订单

读取 `/v2/posting/fbo/list` 和详情时，应保留：

- posting 编号；
- 订单/创建/发货/交付/取消时间；
- 状态；
- SKU、数量和价格；
- 财务与分析附加数据；
- 仓库/集群信息（若提供）；
- 取消、退货和关联流水。

订单事实与财务事实分表保存，再用 posting、SKU、操作标识和时间窗关联。

## 8. 项目优先功能

1. FBO 供应看板：计划、发运、到仓、验收、差异。
2. FBO 库存驾驶舱：仓 × SKU × 状态。
3. 补货建议：销量、周期、安全库存、在途。
4. 长仓和滞销预警。
5. 入仓差异与补偿追踪。
6. 供应、库存、销售、退货、费用的闭环。

## 9. 官方页面级核验：供应申请

> 核验页面：`/libra/fbo/process-details/chto-nujno-znat-o-zayavkah-na-postavku`
>
> 核验日期：2026-07-30

已确认规则：

- FBO 必须先创建供应申请，才能把商品供应到 Ozon 仓。
- 货件/货位（грузоместо）是交付商品所使用的托盘或箱子。
- 创建供应申请后需要填写商品所在货件的组成。
- 未填写货件组成，或验收时发现实物与申请不一致，Ozon 可能收取额外服务费。
- 如需把单个申请的箱数上限提高到 1500，需要创建运输货件。
- 不能加入禁止在 Ozon 销售、禁止 FBO 销售或禁止供应到目标仓的商品。
- “发运准确率”按 0–100% 衡量；核验页面标注低于 10% 为临界水平。减少已预约数量、临时取消或未到仓会影响指标，并可能导致限制。
- 部分供应需要生成 УПД-2，并通过 EDI 交给 Ozon 签署；提交时机取决于商品或目标仓。
- 当仓库/集群只能接收部分数量时，可选择保留可接收数量，或完全移除不能全部接收的商品。该选择只作用于当前申请。
- 供应可能产生跨仓转运、Ozon 上门取货、验收纠正、分区分拣、盈亏处理等费用。
- 创建申请时展示的是费用预测；最终费用在验收后计算。

项目映射：

- `fbo_supply_orders` 应保存申请数量、仓库可接收数量、卖家最终选择和变更历史。
- `fbo_cargoes` 应保存箱/托盘组成，并对缺失或验收差异产生告警。
- 新增 `shipment_accuracy` 指标快照和临界告警，但阈值必须带规则核验日期。
- 费用模型应同时保存 `forecast_cost` 与 `final_cost`，不能用预测费用做结算。
- 供应申请应保存商品准入检查结果、目标仓限制和 УПД-2 模式。

## 11. 官方页面级核验：库存与流动性

> 核验页面：`/libra/fbo/rabota-so-stokom/upravlenie-ostatkami-i-likvidnost-tovarov`
>
> 页面日期：2026-07-14；核验日期：2026-07-30

官方报表：

- FBO → 库存管理可按商品或配送集群查看库存与流动性。
- 商品可按名称、货号或 SKU 搜索，并按流动性、商品标记、类目、集群、仓库或仓库类型过滤。
- XLSX 报告包含说明、商品-仓库、商品汇总、集群汇总四类工作表。
- 报告每日更新多次，并在页面显示最后更新时间。因此本地同步必须保存源数据更新时间，不能假设实时。

官方计算口径：

- 库存可售天数＝可售库存÷过去 28 天平均日销量。
- 过去 28 天平均日销量＝28 天全部订单量÷商品有库存的天数。
- 缺货风险：库存覆盖不超过 28 天。
- 非常畅销：约 28–56 天。
- 畅销：约 56–120 天。
- 过量：超过 120 天。
- 新品数据收集：首次供应后的 28 天内数据不足。
- 无销售：连续 28 天没有销售。
- 无销售且受限：所有集群超过 120 天无销售；不能加入新供应申请，也不能增加现有申请中的数量，但仍可继续销售现有库存。
- 无库存商品还会保留最近 56 天的历史流动性状态。

库存状态至少包括：

- 可售；
- 准备销售；
- 追踪商品等待 УПД；
- 无追踪码、等待取回；
- 临期；
- 供应验收发现的残次；
- 现有库存残次；
- 无法识别的供应盈余；
- 检查中；
- 已创建但未发运的供应申请；
- 运输到仓；
- 买家取消/退货后返回 Ozon 仓；
- 无法识别的商品；
- 按卖家申请准备取回。

其他规则：

- 为减少验收时按存放区域分拣的费用，同一货件应尽量只放同一存放区域的商品。
- 无追踪码商品需要先下架并取回，补充追踪码后重新供应，并通过 УПД 传递追踪码。

项目映射：

- 当前补货算法应采用 Ozon 的 28 天口径作为“平台口径”，同时保留可配置的管理口径。
- 库存事实表必须包含 `source_updated_at`、集群、仓库、库存状态和在途阶段。
- UI 应显示平台流动性状态、平台覆盖天数和本地预测三者，不能混成一个指标。
- 对“无销售且受限”商品禁止生成补货建议。
- 新品 28 天内应标记为数据不足，避免用低样本做确定预测。
- 长仓/取回决策应纳入残次、临期、无追踪码和无法识别库存。

## 12. 对 ozon-workbench 的首轮匹配度审计

> 审计日期：2026-07-30
>
> 本节是把已核验的 FBO 规则映射到当前项目，不代表新增官方页面核验。

### 已有能力

- 已通过 `/v2/posting/fbo/list` 同步 FBO 出库货件；
- 已通过 `/v4/product/info/stocks`、`/v2/analytics/stock_on_warehouses` 和 `/v1/analytics/turnover/stocks` 获取库存、仓库及周转信息；
- 已保存 `fbo_postings`、`stock_rows` 和 `inventory_snapshots`；
- 前端已有库存页、仓库汇总、低库存列表和简单缺货风险；
- 财务模块已能识别 FBO 仓储等服务费用。

### 与官方 FBO 工作流的主要缺口

1. **没有供应申请实体**：无法保存计划数量、目标仓、预约时间、申请状态和变更历史。
2. **没有货件/货位组成**：无法核对箱、托盘及其 SKU 组成，也无法解释因货件信息缺失产生的费用。
3. **没有入仓状态机**：当前“在途”主要描述销售订单到客/退回，不能代表供应申请到 Ozon 仓的在途。
4. **没有验收差异账**：计划、实际发运、仓库验收、盈余、短缺、残次尚未形成可追踪链路。
5. **没有供应费用预测与结算对照**：跨仓运输、上门取货、分拣、纠错等预测费用尚未与最终财务流水关联。
6. **库存口径仍偏简单**：页面中的固定“低库存 ≤10 件”不符合官方按 28 天销量计算覆盖天数的口径。
7. **缺少官方流动性状态**：新品数据收集、无销售、无销售且受限、过量等状态尚未独立保存和展示。
8. **缺少规则时间戳**：阈值和限制会变化，当前实现没有统一保存 `rule_verified_at`。

- `shipped_qty`、`accepted_qty`；
- `surplus_qty`、`shortage_qty`、`defect_qty`；
- `eligibility_status`、`restriction_reason`。

`fbo_cargoes`

- `supply_order_id`、`cargo_id`、`cargo_type`（箱/托盘）；
- `barcode`、`storage_zone`；
- `composition_completed`、`composition_updated_at`；

- `act_number`、`claim_status`、`compensation_amount`；
- `detected_at`、`resolved_at`。

### 推荐的入仓状态分层

在拿到官方“跟踪供应申请”页面的完整状态清单前，项目先使用稳定的业务阶段，不提前硬编码俄文状态：

`draft → submitted → scheduled → ready_to_ship → in_transit_to_warehouse → arrived → accepting → accepted`

另外保留终止/异常分支：

- `cancelled`：申请取消；
- `rejected`：不符合接收条件；
- `partially_accepted`：部分验收；
- `acceptance_discrepancy`：存在数量或质量差异；
- `unknown`：Ozon 新增或尚未映射的原始状态。

必须同时保存 `raw_status`。业务阶段用于项目内聚合，原始状态用于追溯和规则更新。

3. 新建供应申请、供应商品、货件、事件、验收差异五组表。
4. 新建 FBO 供应看板：计划、待发运、入仓在途、验收中、已验收、异常。
5. 建立 `requested → shipped → accepted → sellable` 数量对账。
6. 把供应预测费用与财务最终费用分开保存并做差异告警。
7. 对“无销售且受限”的 SKU 停止生成补货建议。
8. 所有动态阈值显示来源页面和核验日期。

## 13. 2026 年 FBO 跨仓供应的集群化变更

> 官方来源：Ozon for developers，〈Изменения в методах Seller API при работе с поставками FBO〉
>
> 官方发布日期：2026-01-19；生效日期：2026-02-16；核验日期：2026-07-30
>
> 适用范围：仅限跨仓（cross-docking）FBO 供应申请。

官方确认：

- `/v3/supply-order/get` 与 `/v1/supply-order/details` 的响应新增 `macrolocal_cluster_id`；
- `storage_warehouse.arrival_date` 将始终返回 `null`，不能再把它作为预计到仓时间；
- 对跨仓供应，`warehouse_id` 不再是有效的业务定位依据；
- 跨仓供应应以 `macrolocal_cluster_id` 作为目标归属；
- 跨仓供应草稿按集群而不是具体仓库计算；
- 可选时隙按集群而不是具体仓库提供；
- 最终供应申请也按集群而不是一个或多个具体仓库生成；
- 直接供应到具体仓库不在本次变更范围内。

### 对项目数据模型的修正

- `fbo_supply_orders.target_cluster_id` 对跨仓供应必须是核心字段，不能只作为展示信息；
- `target_warehouse_id` 必须允许为空，并标明它对跨仓供应可能不再适用；
- 增加 `supply_route_type`：至少区分 `direct` 与 `cross_docking`；
- 时隙实体需要同时保存 `scope_type` 与 `scope_id`，避免默认绑到仓库；
- `storage_warehouse_arrival_date` 允许为空，不得据此生成“预计到仓”承诺；
- 仓库名称为空不能自动判为数据同步失败，应结合路线类型与 `macrolocal_cluster_id` 判断；
- 历史记录不能用新集群值覆盖旧仓库值，应保存接口版本和源响应。

### 对 UI 与补货逻辑的修正

- 跨仓供应列表优先显示目标集群，具体仓库只作为平台后续分配结果；
- 时隙选择器应显示“集群时隙”或“仓库时隙”，避免误导；
- 补货推荐先决定集群覆盖，再决定直送或跨仓路线；
- 不得把“仓库未知”与“供应目的地未知”混为一类异常；
- 到仓预测必须使用供应状态、时隙及实际物流事件，不能读取恒为空的字段。

### 当前项目风险

ozon-workbench 目前主要按 `warehouse_name` 汇总库存，并且尚未建立供应申请模型。如果直接新增供应功能却仍以仓库为唯一目标维度，将无法正确表达 2026 年后的跨仓 FBO 供应。

## 14. FBO 运输货件与可信验收

> 官方信息核验日期：2026-07-30。

Ozon 将供应申请中的运输单元区分为箱和托盘。供应自动化必须记录每个运输货件的准确组成，而不是只保存供应申请总数量。

2025-09-03 起，Ozon 对 FBO 可信验收采用了更严格的“单 SKU 运输货件”规则：

- 箱或托盘只包含一个 SKU 时，属于单 SKU 运输货件；
- 包含多个 SKU 时，属于混合运输货件；
- 单 SKU 运输货件可启用可信验收；
- 免费验收还依赖正确填写有效期，并且不存在残次、盈余或短缺；
- 可信验收可能在入库时不立即逐件核验，而是在后续订单环节发现差异；
- 因此“已入库”不能等同于“最终无差异”。

项目数据模型应补充：

- `cargo_composition_type`: `mono_sku` / `mixed_sku`；
- `trusted_acceptance_enabled`；
- `expiry_data_complete`；
- `initial_acceptance_at` 与 `discrepancy_detected_at`；
- `acceptance_provisional`：标记验收结果是否仍可能后置调整；
- 差异发现来源：入库核验、后续拣货、订单履约或卖家申诉。

### 货件组成的项目验收条件

- 每个箱/托盘都有平台货件 ID 和条码；
- 每个货件能下钻到 SKU、计划数量和实际数量；
- 不允许用供应申请总量平均分配到货件；
- 货件组成提交失败必须可重试且幂等；
- 修改货件组成后保存版本，不覆盖历史；
- 验收差异能关联到货件、SKU、供应申请和财务费用；
- 混合存放区域提前提示可能产生分拣费用；
- 费率只从带生效日期的规则表读取。

## 15. 2026-07 FBO 动态经营规则

> 以下为时效性很强的官方公告，核验日期为 2026-07-30；不得写死为长期费率。

### 跨仓和上门取货费率

Ozon 于 2026-07-23/24 调整部分 FBO 费用：

- 若干指定集群的跨仓“配送到仓”阶段临时为 0 ₽，公告有效期截至 2026-09-15；
- 从仓库或分拣中心发运的箱/托盘处理费阶段性降为 0 ₽/升；
- 上门取货按箱和托盘采用统一的每升费率；
- 上门取货的固定出车费用同步下调。

这些值属于动态、区域化且可能再次调整的费率。项目只能保存：

- `fee_rule_id`；
- `route_from`、`route_to_cluster`；
- `cargo_type`；
- `rate_per_liter`、`fixed_fee`；
- `effective_from`、`effective_to`；
- `source_url`、`verified_at`。

不能把公告中的金额直接写进计算代码。

### 本地销售

Ozon 最新公告计划于 **2026-08-30** 启动新的 FBO 本地销售机制：

- 商品位于买家所在集群时，可能获得本地销售费率优惠；
- 官方建议依据“本地性销售”页面的低本地销售占比和补货建议安排供应；
- 先前公告的 2026-07-31 启动日期及 6 个百分点优惠已被后续公告撤回；
- 2026-08-30 计划仍属于未来规则，落地前必须再次核验。

项目应预留：

- SKU × 买家集群的本地/非本地订单标识；
- 本地销售占比；
- 因本地性产生的费率优惠；
- 目标集群缺货与建议补货数量；
- 公告版本、生效日期和撤回状态。

## 16. 官方页面级核验：创建供应申请

> 核验页面：`/libra/fbo/process-details/sozdanie-zayavki-na-postavku`
>
> 核验日期：2026-07-30

### 创建流程

官方当前流程为：

1. 在 FBO → 供应申请中创建申请；
2. 选择一个或多个目标集群；
3. 为每个集群添加商品和数量；
4. 为各集群选择交货方式，或把多个集群合并为统一发运；
5. 检查存储仓/集群分配；
6. 选择发运日期和时隙；
7. 创建后继续填写运输货件组成、有效期、标签、车辆和司机信息。

商品和交货方式可以按任意顺序选择，但官方建议先添加商品。这样系统才能推荐可用交货点、可用性和最近时隙。

### 补货推荐与商品准入

- 官方按集群展示建议补货商品和数量；
- 默认建议周期为 28 天；
- 可切换为 7、14、28 或 56 天；
- 推荐口径与“商品可用性”栏目一致；
- 商品可以逐个添加，也可以通过文件导入；
- 支持按商品名称、货号或 SKU 搜索；
- “无销售且受限”的商品不能加入申请，也不能增加已创建申请中的数量；
- 可以批量移除“无销售”和“过量”商品；
- 商品出现错误标记时需要检查供应限制；
- Super 商品可能影响奖励，但不能因此绕过库存和利润判断。

项目必须同时保存：

- `recommendation_period_days`；
- `recommended_qty` 与 `seller_selected_qty`；
- 推荐生成时间和来源集群；
- 商品流动性状态；
- 准入结果和限制原因；
- 用户是采用推荐、手工输入还是文件导入。

### 交货方式

每个集群可以使用不同方式：

- 卖家自行送到仓库/交货点；
- Ozon 上门取货；
- 跨仓交货。

也可以把多个集群合并为统一发运，在同一交货点和时隙交货。官方建议先从 2–3 个集群组合测试，因为集群越多，越难找到共同可用日期。

系统会记住各集群最近选择的交货方式和交货点，在新草稿中预填；如果保存的交货点不可用，则不会自动使用。

项目应区分：

- `delivery_method`：自行、上门、跨仓；
- `shipment_group_id`：属于哪一次统一发运；
- `dropoff_point_id`；
- `saved_preference_applied`；
- `preference_unavailable_reason`。

### 存储仓和集群显示

- 对跨仓和 Ozon 上门取货，界面不展示具体存储仓名称；
- Ozon 会在集群内把商品分配到合适且有容量的仓库；
- 运输货件标签只显示集群名称，不显示具体仓库；
- 验收完成后，需要从 FBO → 库存管理查看商品最终所在仓库；
- 如需发送 УПД，应使用 Ozon 在 XML 模板中提供的地址；
- 因此，仓库为空在这些路线中是正常业务状态。

### 时隙

- 可在创建过程中或创建后选择发运时隙；
- 时隙尚未过期时可以修改；
- 单集群配送展示该集群的最近日期；
- 统一发运展示所有参与集群共同可用的最近日期；
- 统一发运中的某个集群可能把共同日期明显推后；
- 卖家可以移除该集群，或为其改用另一种交货方式；
- 选择日期和时间后，草稿进入“填写数据”状态。

项目需要保存每个候选时隙和不可用原因，不能只保存最终选中的时隙。

### 当前页面公布的体积上限

> 这些上限属于动态规则，必须保存核验日期，并在实施写操作前重新核对。

- 送到分拣中心或仓库：申请总体积不超过 **100,000 升**；
- 交给 Ozon 上门取货或送到自提点：不超过 **1,000 升**；
- 部分自提点上限为 **500 升**；
- 送到 ППЗ：不超过 **11,000 升**，部分 ППЗ 上限可能更低；
- 系统会自动计算每件商品及各集群商品清单的升数；
- 单独跨仓/自行配送时，上限分别作用于申请中的每个集群；
- 统一发运时，上限作用于所有加入统一发运的集群总体积；
- 超限后不能进入下一步，只能拆成多个申请；
- 每个拆分后的申请需要使用单独车辆交货。

数据模型必须保存平台计算体积与本地复算体积：

- `platform_volume_liters`；
- `calculated_volume_liters`；
- `volume_limit_liters`；
- `limit_scope`：集群或统一发运；
- `limit_source_point_type`；
- `rule_verified_at`。

### 创建完成后的必做事项

申请创建后出现在 FBO → 供应申请，状态为“填写数据”。随后必须：

- 填写运输货件组成和商品有效期；
- 下载全部商品及货件标签；
- 如果送到分拣中心或仓库，填写车辆与司机信息；
- 按要求包装商品；
- 检查申请状态；
- 准备并交付供应；
- 跟踪验收；
- 必要时编辑或删除申请。

因此，项目不能把 `submitted` 当成可发运。至少要增加：

- `composition_complete`；
- `expiry_complete`；
- `labels_ready`；
- `vehicle_driver_complete`；
- `packaging_confirmed`；
- `ready_to_ship`。

只有所有适用前置条件满足后，才能进入项目内部的“可发运”阶段。

## 17. 官方页面级核验：创建申请时的限制

> 核验页面：`/libra/fbo/process-details/ogranicheniya-po-skaldam`
>
> 核验日期：2026-07-30

### 限制来源

商品可能无法加入供应申请，原因至少包括：

- 商品禁止在 Ozon 销售；
- 商品允许销售，但禁止使用 FBO；
- 商品卡缺少强制追踪/标记信息或 ТН ВЭД 编码；
- 目标仓库或集群不接收该商品；
- 商品处于“无销售且受限”状态；
- 仓库容量暂时不足；
- 申请中的商品类型或数量组合不符合接收条件。

项目必须把限制拆成结构化原因，不能只保存一条“商品不可供应”错误。

建议枚举：

- `platform_sale_prohibited`；
- `fbo_prohibited`；
- `marking_required`；
- `tnved_required`；
- `warehouse_restricted`；
- `cluster_restricted`；
- `capacity_temporarily_unavailable`；
- `liquidity_restricted`；
- `quantity_partially_allowed`；
- `supply_type_mismatch`。

### 全局尺寸和重量限制

当前官方页面说明，所有仓库都不接收超过以下任一上限的商品：

- 长度：220 cm；
- 宽度：120 cm；
- 高度：80 cm；
- 重量：120 kg。

这些是动态准入规则，必须保存来源和核验日期。项目应在创建申请前校验商品主数据，并区分“商品尺寸超限”和“运输货件尺寸超限”。

### 混合申请与部分接收

- 普通商品、大件商品和需要 УПД 的商品混入同一申请，可能导致仓库只能接收其中一部分；
- 平台会给出“不接收”商品列表，并允许下载；
- 可接收商品可以继续供应，其余商品应针对合适仓库另建申请；
- 网站端允许卖家检查并编辑未通过商品；
- 若卖家不修改，平台会移除未通过商品；
- 移动应用会自动移除受数量限制的商品，卖家不能撤销。

因此需要保存三种数量：

- `requested_qty`；
- `platform_allowed_qty`；
- `final_application_qty`。

并保存：

- `removed_by_platform`；
- `removed_surface`：网页或移动端；
- `rejection_report_url` 或报告归档标识；
- `restriction_checked_at`。

### 仓库临时容量限制

仓库没有可用存放空间时，会临时停止接收相关商品。官方临时限制表位于：

`分析 → 供应规划 → 商品可用性`

临时容量限制不能固化为永久商品禁令。项目应设置有效期和下一次复查时间。

### 追踪标识、ТН ВЭД、GTIN 和统一计量单位

对于受追踪或强制标记商品，平台可能要求商品卡提供：

- 10 位 ТН ВЭД ЕАЭС 编码；
- 13 位 GTIN；
- 统一计量单位数量。

统一计量单位数量与销售件数不一定相同。例如一套包含 3 件商品，销售数量为一套，但统一计量单位可能为 3 件。缺少必要信息时不能加入供应。

项目商品主数据需要区分：

- `sellable_unit_qty`；
- `uniform_measurement_qty`；
- `gtin`；
- `tnved_eaes_code`；
- `traceability_required`；
- `mandatory_marking_required`。

### 部分通过商品的全局处理规则

网站端可设置所有新申请的默认策略：

- `remove_entire_sku`：只要目标集群不能接收全部数量，就整项删除；
- `keep_allowed_qty`：保留该 SKU，但把数量降至集群可接收数量。

该设置可以在申请列表的“设置和费率”中修改，也可在草稿的“不接收”页修改；修改后作用于当前及后续新申请。

移动应用不提供该设置，默认自动删除部分通过的商品。

项目必须保存当时实际采用的策略快照，不能只读取账户当前设置来解释历史申请。

## 18. 官方页面级核验：编辑或取消供应申请

> 核验页面：`/libra/fbo/process-details/otmenit-zayavku-na-postavku`
>
> 核验日期：2026-07-30

### 店铺边界

供应申请只能在创建它的店铺内编辑。多店铺系统的所有修改、取消和时隙操作必须以 `shop_id + supply_order_id` 为边界，禁止跨店铺复用编号。

### 草稿删除

- 草稿若 7 天内未转成正式申请，平台会自动删除；
- 创建过程中可以主动删除草稿；
- 删除后通常不可恢复；
- 从申请列表删除时仅有约 3 秒的撤销窗口；
- 超过撤销窗口后不能恢复。

项目应保存：

- `draft_expires_at`；
- `deleted_at`；
- `delete_source`；
- `undo_deadline_at`；
- `deletion_final`。

不能把 UI 的短暂撤销能力设计成长期“软删除恢复”承诺。

### 正式申请取消

- 正式申请取消后不能恢复，只能重建；
- 应在确认无法交货时尽快取消，以释放时隙；
- 可以取消单个子供应，也可以取消整个申请；
- 当所有子供应都被取消时，父申请自动进入“已取消”并移入归档；
- “发运协调”状态下不能取消整个申请，但仍可编辑；
- 被取消或未发运的集群不计入验收差异统计。

父申请与子供应必须分别保存状态。父状态不能简单覆盖所有子供应。

### 已发送 УПД-2 时的取消前置条件

若供应必须使用 УПД-2，且文件已经通过 EDI 发出并绑定到待取消供应：

1. 必须先撤销 УПД-2；
2. 使用 Контур.Диадок 或 СберКорус 时可自行撤销；
3. 使用漫游交换时，应在 EDI 服务商处撤销；
4. 随后联系 Ozon 支持，从 Ozon 一侧删除文件绑定；
5. 文档解绑完成后再执行供应取消。

项目需要状态链：

`document_bound → annulment_requested → annulled_provider_side → unbound_ozon_side → cancellation_allowed`

### 修改商品清单的时间限制

当前页面规定：

- Ozon 上门取货：最晚在交货前 2 天修改；
- 其他交货方式：最晚在交货前 1 小时修改。

这些限制同样适用于修改日期和时隙。

修改商品数量、选择时隙后减少数量、取消供应或未到仓，都可能降低“发运准确率”。

以下场景不能编辑：

- 交货到 `Тверь_Хаб`；
- Ozon Fresh 暗店供应。

### 可修改内容和二次校验

可手动或通过文件修改：

- 添加商品；
- 删除商品；
- 改变已有商品数量。

修改后平台自动重新计算体积，并重新检查商品准入。可能阻止添加的原因包括：

- 目标仓不接收；
- 商品不适用当前供应类型，例如需要 УПД；
- 商品为“无销售且受限”；
- 发运准确率较低，平台已对各集群的供应数量实施限制。

项目编辑流程必须重新运行全部准入、体积、文档和准确率校验，不能只更新数量字段。

### 修改时隙

- 上门取货最晚提前 2 天；
- 其他方式最晚提前 1 小时；
- 发运准确率较低时，每个申请最多只能调整时隙 2 次；
- 平台会显示剩余可调整次数。

需要保存：

- `timeslot_change_count`；
- `timeslot_change_limit`；
- `remaining_timeslot_changes`；
- 每次变更的旧时隙、新时隙、操作者和时间；
- 变更是否影响发运准确率。

## 19. 官方页面级核验：拆分供应申请

> 核验页面：`/libra/fbo/process-details/supply-application-split`
>
> 核验日期：2026-07-30

### 父申请与子供应

当创建申请时选择多个集群，系统会把一个申请拆成多个供应。拆分结果不是仅供展示的分组，而是独立的实物交付和验收单元。

数据模型需要明确：

- `application_id`：父申请；
- `supply_id`：子供应；
- `target_cluster_id`；
- `split_reason`：集群、交货方式、商品类型、尺寸或特殊接收条件；
- `split_generated_by_platform`；
- `merge_allowed`。

### 多个子供应的交货要求

每个子供应必须：

- 使用独立托盘或独立箱子；
- 准备独立文件，例如 УПД 或珠宝规格表；
- 使用自己的运输货件标签；
- 在约定时隙交货。

不同子供应的商品不能装入同一个运输货件并粘贴两个标签，否则平台拒绝接收。

项目必须在装箱校验中强制：

`一个 cargo_id 只能属于一个 supply_id`

不能允许货件跨子供应共享，即使它们属于同一个父申请或使用同一辆车。

### 同车运送多个子供应

多个供应可以使用同一车辆，但需要：

- 交货日期一致；
- 车辆信息一致；
- 各子供应选择相邻时隙；
- 按顺序连续完成交货。

因此车辆应建模为发运批次资源，而不是直接嵌入单个供应：

- `dispatch_batch_id`；
- `vehicle_id`；
- `driver_id`；
- `delivery_date`；
- `supply_sequence`；
- `timeslot_from`、`timeslot_to`。

### 霍鲁格维诺特殊拆分

在 Хоругвино，系统可能按商品类型、尺寸和价值自动拆分：

- 因类型或尺寸产生的拆分不能重新合并；
- 贵重商品与不同尺寸类型商品需要特殊接收、存储和发运条件；
- 大件和长件建议先装车，因为平台最后接收，标签会有对应标记；
- 贵重商品建议最后装车，因为平台优先接收，标签会有特殊标记。

项目不应把装车顺序当作普通 SKU 排序。需要保存平台标签标记和建议的卸货优先级：

- `cargo_handling_class`；
- `platform_label_marks`；
- `loading_priority`；
- `unloading_priority`；
- `special_acceptance_required`。

## 20. 官方页面级核验：跟踪供应申请

> 核验页面：`/libra/fbo/process-details/kak-otslejivat-zayavki-na-postavku`
>
> 核验日期：2026-07-30

### 列表需要呈现的事实

供应申请列表至少显示：

- 申请编号和状态；
- 已选择的交货时间与交货点；
- 最终集群与存储仓；
- 父申请拆成的子供应数量；
- 商品种类数和总件数；
- 创建日期。

可以跨店铺查看申请，但仍只能在原店铺编辑。若下一步有时间限制，平台会显示倒计时。

不同集群采用不同交货方式时会生成多个子供应；统一发运则表现为一个父申请包含多个子供应。

### 官方状态生命周期

#### 准备阶段

- `Черновик`（草稿）：数据尚未填写完整；位于“准备供应”页。
- `Заполнение данных`（填写数据）：需要填写货件数、车辆、司机及适用的商品文件。
- `Готово к отгрузке`（可交货）：等待约定日期，卖家可前往交货。

#### 交货与运输阶段

- `Принято на точке отгрузки`（交货点已接收）：商品已接收，准备发往最终仓。
- `Отказано в отгрузке`（交货被拒）：暂时无法接收；错误状态可能在 72 小时内由平台纠正。
- `В пути`（在途）：子供应正在运往最终仓，通常持续数天。

“交货被拒”并非立即等同于最终失败：

- 若只是包装问题，平台可能要求卖家现场修正；
- 状态保持期间可按现场队列重新交货；
- 若不是误判，之后会进入“未接收”并归档。

#### 入仓与文件阶段

- `Приёмка на складе`（仓库验收）：拆包并核对数量和残次；
- `Согласование актов`（验收文件确认）：平台已生成验收结果文件；
- `Спор`（争议）：卖家未同意验收文件，平台处理中；
- `Завершено`（完成）：文件签署完成，商品已进入销售。

只要任一子供应开始仓库验收，父申请就可能显示“仓库验收”，即使其他子供应仍在途中。因此父状态是聚合状态，不能替代子供应状态。

无 EDI 的供应进入“验收文件确认”后，卖家有 **5 个日历日**接受文件或提交异议。

#### 终止状态

- `Не принято`（未接收）：因违反接收规则而最终未接收；
- `Отменено`（已取消）：卖家取消；
- `Просрочено`（已过期）：未在期限内选择交货日期/交货点，或未按时隙送达。

官方说明，选择日期和交货点通常只有约 **60 分钟**。超时后旧申请归档，需要新建申请。

### 推荐的项目状态映射

项目内部状态不能丢弃官方原始值：

| 官方状态 | 项目阶段 | 是否终态 |
|---|---|---|
| `Черновик` | `draft` | 否 |
| `Заполнение данных` | `data_completion` | 否 |
| `Готово к отгрузке` | `ready_to_ship` | 否 |
| `Принято на точке отгрузки` | `accepted_at_dropoff` | 否 |
| `Отказано в отгрузке` | `dropoff_rejected_pending` | 否 |
| `В пути` | `in_transit_to_warehouse` | 否 |
| `Приёмка на складе` | `warehouse_acceptance` | 否 |
| `Согласование актов` | `acceptance_documents_review` | 否 |
| `Спор` | `dispute` | 否 |
| `Завершено` | `completed` | 是 |
| `Не принято` | `not_accepted` | 是 |
| `Отменено` | `cancelled` | 是 |
| `Просрочено` | `expired` | 是 |

必须保存：

- `raw_status`；
- `normalized_status`；
- `status_changed_at`；
- `status_source_updated_at`；
- `is_terminal`；
- `action_deadline_at`；
- `next_required_action`；
- 状态事件历史。

### 虚拟供应

虚拟供应是 Ozon 为修正物流或验收遗漏而创建的供应，例如部分商品在第一次验收时未被处理。

规则：

- 列表中带“虚拟”标记；
- 卖家不能编辑；
- 验收完成并进入文件确认后，仍需确认文件或通过 EDI 处理；
- 某些商品仍可能需要 УПД；
- 珠宝可能需要 УПД 和规格表。

项目应增加：

- `is_virtual_supply`；
- `virtual_reason`；
- `created_by_platform`；
- `editable = false`；
- `source_supply_id`；
- 虚拟供应与原供应的数量差异关联。

### 关键告警

至少需要：

- 申请交货点/日期选择倒计时；
- 填写数据截止时间；
- 交货被拒后 72 小时复核窗口；
- 验收文件 5 日确认截止；
- 子供应状态不一致；
- 虚拟供应新建；
- 争议未关闭；
- 已过期需要重建申请。

## 23. 官方页面级核验：发运准确率

> 核验页面：`/libra/fbo/process-details/tochnost-otgruzok`
>
> 核验日期：2026-07-30

### 指标定义

发运准确率衡量卖家选定交货日期和时段后，实际保留并按约交付的商品数量。指标范围为 0–100%，官方当前临界线为 **低于 10%**。

会降低指标的行为：

- 选定时段后减少申请内商品数量；
- 取消供应申请；
- 承诺交货但未送达仓库或交货点。

### 计算规则

平台分析不含当天的最近 **28 天**内已交货或已取消供应：

`发运准确率 = 交货时所有供应的最终商品数量 ÷ 选定时段后各供应曾达到的最大商品数量`

其中：

- 分子是供应交货时的最终件数；
- 分母是选择时段后曾提交的最大件数，即使后来又减少也使用峰值；
- 取消或未送达的供应，分子按 0 计算；
- 虚拟供应不参与计算。

若最近 28 天没有交货或取消记录，平台展示最近 6 个月的最后已知值；6 个月也无记录，则从首次供应开始计算，最初 28 天不施加限制。

项目必须保存事件级快照，不能用最终申请数量反推历史：

- `timeslot_selected_at`；
- `max_qty_after_timeslot`；
- `max_qty_recorded_at`；
- `final_qty_at_dispatch`；
- `cancelled_or_no_show`；
- `included_in_accuracy`；
- `calculation_window_from/to`；
- `accuracy_value`；
- `calculated_at`。

### 低准确率限制

指标低于临界线时，平台可能：

- 禁止创建未选择日期和时段的供应申请；
- 将每个申请的时段调整限制为最多 2 次；
- 按集群限制可供应商品数量。

临近临界线时，平台会在卖家后台和邮件中告警，邮件最多每周一次。

项目应将临界线和限制作为带核验时间的动态策略保存，而不是写死为永久规则：

- `accuracy_critical_threshold`；
- `restriction_active`；
- `timeslot_change_limit`；
- `cluster_qty_limit`；
- `policy_verified_at`。

### 备用供应

限制期间，每个集群可使用一次限量备用供应，以改善指标并解除限制。以下任一行为都可能视为开始使用该集群的备用供应：

- 创建新供应申请；
- 向已有且已选时段的申请添加商品；
- 为已有申请选择时段。

备用供应目前只能在网页卖家后台创建，移动应用不支持。开始备用供应后，在其交付前：

- 不能增加该集群其他申请的商品数量；
- 不能创建新的该集群供应；
- 不能为该集群已有申请选择时段。

备用供应最多可取消 2 次；耗尽取消次数后，需要完成现有备用供应。

建议模型：

- `reserve_supply_id`；
- `reserve_cluster_id`；
- `reserve_qty_limit`；
- `reserve_started_at`；
- `reserve_cancel_count`；
- `reserve_cancel_limit`；
- `reserve_consumed`；
- `reserve_released_at`。

### 明细与追溯

后台可下载 xlsx 明细，包含“按供应”和“按日期”两页。供应维度至少包括供应 ID、选择时段后的最大件数及日期、交货时最终件数、交货或取消日期；日期维度包括每日指标、计算区间和非标准 28 天窗口的原因。

当前页面说明，明细文件纳入自 **2026-05-15** 起创建、交货和取消的供应数据。项目导入时应保留来源文件日期和官方覆盖起点，避免把缺失的更早记录误判为 0。

## 24. 官方页面级核验：货件基础规则

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/chto-nujno-znat-o-gruzomestah`
>
> 核验日期：2026-07-30

### 货件与数量上限

货件是交给 Ozon 仓库的箱或托盘。当前一笔供应可接收：

- 最多 30 箱；
- 最多 40 托盘。

每个箱或托盘都必须粘贴自己的货件标签。

需要更多箱时，可建立“运输货件”：把箱子放在运输托盘上，箱数上限可提升至 1500，每箱最多 230 个不同 SKU。此类供应不能交到自提点。运输货件同时需要箱标签和运输托盘标签。

这些属于动态运营限额，项目应保存核验时间：

- `cargo_place_type`：box / pallet / transport_pallet；
- `cargo_place_count`；
- `box_limit`；
- `pallet_limit`；
- `transport_box_limit`；
- `sku_count_per_box`；
- `dropoff_point_allowed`；
- `limit_verified_at`。

### 商品组成与分区

未填写货件组成，或实物与申报组成不一致，会产生额外验收服务费。

货件按组成分为：

- 单 SKU 货件：一个货件只含同一 SKU，可包含任意件数；
- 混合货件：一个货件含多个 SKU。

为减少验收排序费，应尽量：

- 每个货件只装同一 SKU；
- 每个货件只装同一存放分区的商品。

项目需要在装箱时校验：

- `declared_sku_qty` 与实际扫描数量；
- 一个货件内的 SKU 数量；
- 一个货件内是否混合存放分区；
- 单 SKU/混合货件分类；
- 可能产生的额外服务费原因。

### 保质期

适用商品必须填写保质期。未填写或实际保质期与申报不符，会产生保质期处理费。

同一 SKU 的不同保质期批次必须放入不同货件，因为每个货件对该商品只能申报一个保质期。建议使用：

- `batch_id`；
- `expiration_date`；
- `cargo_id`；
- `declared_expiration_date`；
- `actual_expiration_date`；
- `expiration_mismatch`。

### 标签不可复用

缺少商品标签或货件标签时，仓库不接收供应。删除货件后，其标签不能用于另一个货件，否则无法接收。

标签应当是不可复用标识：

- `cargo_label_id` 永久绑定原 `cargo_id`；
- 删除货件时标签进入 `void`；
- 禁止把 `void` 标签重新绑定；
- 运输货件同时验证箱标签和托盘标签。

### 何时必须填写货件组成

当前页面规定：

- 经自提点跨仓，以及发往加里宁格勒 МРФЦ、明斯克 МПСЦ、阿拉木图-2、阿斯塔纳 РФЦ 的供应必须填写；未填写即拒收；
- 指定珠宝仓供应不要求填写，未填写不扣该项费用；
- 其他供应可不填，但会收取货件组成处理服务费。

仓库名单和收费标准会变化，执行前必须根据目标仓、供应类型和官方最新费率重新核对。

## 25. 官方页面级核验：添加货件与填写商品组成

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/gruzomesta-v-postavke`
>
> 核验日期：2026-07-30

### 可操作状态与截止时间

供应申请进入“填写数据”后才可创建货件。货件数量和组成的修改截止时间：

- 自送至仓库、自提点或分拣中心：交货前 1 小时；
- Ozon 快递员上门取货：交货前 2 天。

错过原时段后，应在 2 天内先改约时段，再补充或修改货件组成；否则申请进入“已过期”，只能新建申请。

项目必须基于交货方式计算：

- `cargo_edit_deadline_at`；
- `cargo_edit_allowed`；
- `cargo_edit_block_reason`；
- `missed_timeslot_reschedule_deadline_at`。

### 添加与分配

可以手工或通过 XLS 文件填写货件组成。每个申请商品必须分配到具体货件；“添加全部剩余”适合把未分配余量放入最后一个货件。

小件商品应合并装箱，不应一件商品建立一个独立货件，否则平台可能拒收。

项目应维护数量守恒：

`申请商品数量 = 所有货件已分配数量 + 未分配数量`

且必须防止：

- 同一件数被重复分配；
- 超过申请内 SKU 数量；
- 已删除货件仍持有有效分配；
- 实物扫描数与申报数不一致。

### 保质期与存放分区

- 适用商品必须填写保质期；
- 同 SKU 不同保质期必须拆到不同货件；
- 官方只给出月和年时，申请内填该月 1 日；
- 一个货件显示“不同分区”时，应拆分为单分区货件，以避免分区排序服务费。

平台根据组成自动确定单 SKU 货件或混合货件，项目应把官方分类结果与本地推导结果同时保存。

### 货件标签

货件标签推荐 A4（210 × 297 毫米）；小于 **120 × 75 毫米**时条码可能无法扫描。

跨仓或快递员交货时，标签显示目标集群名而不是仓库名。商品标签与货件标签是不同标签，不能混用。

建议校验：

- 每个有效货件有唯一标签；
- 标签尺寸至少 120 × 75 毫米；
- 标签目标集群与供应目标一致；
- 已删除货件的标签已作废；
- 商品标签和货件标签类型正确。

### 运输货件的不可逆选择

运输货件仍属测试能力，不保证所有卖家可见。启用后：

- 普通箱必须全部分配到运输托盘；
- 每个箱都贴箱标签，每个运输托盘贴运输货件标签；
- 运输货件至少保留一个，不能从原申请完全删除；
- 若要改回普通货件类型，需要重建供应申请；
- 不能交到自提点。

项目字段：

- `transport_cargo_feature_available`；
- `transport_cargo_mode_enabled`；
- `transport_pallet_id`；
- `box_id`；
- `box_assigned_to_transport_pallet`；
- `transport_mode_irreversible`；
- `recreate_application_required`。

### 分区类型

官方当前列出：

- 创建供应申请时的集群商品列表；

- 货件组成界面；
- 货件组成 XLS；
- FBO 库存管理。

- `official_placement_zone`；
- `placement_zone_source`；
- `placement_zone_observed_at`；
- `local_predicted_zone`；
- `zone_rule_version`；
- `zone_conflict`。

同一货件混合不同存放分区会产生分区排序费。装箱优化优先级应为：

1. 先满足危险品、温控、珠宝、封闭分区等强隔离要求；
2. 再按官方存放分区拆分；
3. 在同一分区内尽量按 SKU 单装；
4. 最后优化箱数和体积。

## 27. 官方页面级核验：FBO 商品包装

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/package`
>
> 核验日期：2026-07-30

### 通用要求

商品包装必须完整、干燥，并能在运输和仓储过程中保护商品。允许的包装材料包括：

- 透明膜和热缩膜；
- 纸筒；
- 带胶封口袋、拉链袋或安全袋；
- 纸板或瓦楞纸箱；
- 与其他包装组合使用的气泡膜；
- 原厂、工业、专业或专用包装。

禁止使用红色胶带。旧、脏、变形的纸箱以及其他平台的纸箱不应使用。

如果商品外盒承担展示功能，带有图片、说明或商品信息，应再用热缩膜或拉链袋保护；仅用于保护商品的普通运输盒不强制增加该层保护。

商品外包装必须带商品标签。Ozon 运输车辆并非冷藏车，对温度敏感商品的损失风险不能默认由平台承担。

### 包装等级与分类规则

官方分类表为不同品类定义：

- 强制包装类型；
- 最低包装等级；
- 操作标识；
- 附加保护要求。

当一个品类列出多种等级时，基础等级是最低接受标准；风险较高时应选择加强或最高等级。

项目不应把长分类表硬编码在业务逻辑中，应建模为可版本化规则：

- `category_id`；
- `required_packaging_type`；
- `minimum_packaging_level`；
- `handling_marks[]`；
- `additional_requirements[]`；
- `rule_source_url`；
- `rule_verified_at`。

典型规则包括：

- 非玻璃液体：多层热缩膜或缠绕膜，防漏，并标“防潮”“向上”；
- 化妆品、香水、指甲油等容器商品：坚固纸箱、每件密封，易燃品增加“易燃”；
- 散装商品：多层膜，防潮、防抛，并应能承受 1 米跌落；
- 干粉建材：原厂包装加多层缠绕膜或坚固袋，防潮并标毛重；
- 大件和轮式商品：保护角、填充物、固定、相应的大件和禁止翻转标识；
- 电池/蓄电池：密封、绝缘端子并遵守危险品运输要求。

### 潜在危险品

危险或疑似危险商品必须：

- 使用坚固且完全封闭的外包装；
- 用缓冲材料固定，避免内部移动；
- 包装不得有渗漏、潮湿、凹陷或破损；
- 液体竖直放置，密封瓶盖，并标“此面向上”；
- 把商品本体的危险、易碎提示复制到外包装；
- 含电池设备应防止意外启动；
- 电池端子应绝缘并与液体、金属和导体隔离。

### 包装失败的后果

包装不合适时平台仍可能入库，但商品可能在物流中损坏、泄漏或污染相邻商品。相关商品可被无赔偿核销，卖家还需承担销毁费用。

因此项目必须区分：

- `accepted_despite_packaging_risk`；
- `packaging_nonconformity`；
- `damage_caused_by_packaging`；
- `written_off_without_compensation`；
- `disposal_fee`；
- `packaging_reliability_index`。

### 额外加固

包装内商品不得移动或互相碰撞；应使用泡沫、瓦楞纸或其他填充物。袋或箱应尽量承受 1 米跌落。

易碎、大件和重货可采用：

- 托盘围板；
- 木质框架硬包装；
- 由纤维板、木方、托盘和底板组成的硬箱。

镜面、玻璃和卫浴通常至少需要两层气泡膜、保护角、五层纸箱和防移动填充；大件家具、家电需结合原厂包装、缠绕膜、硬质加固以及“易碎”“大件”“向上”“禁止翻转”等标识。

## 28. 官方页面级核验：供应发运准备

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/prepare-supply`
>
> 核验日期：2026-07-30

### 四步准备流程

1. 检查商品保质期、包装后尺寸和重量，并按品类规则包装；
2. 给每件商品粘贴商品标签；
3. 按申请申报组成放入箱或托盘；
4. 给每个货件粘贴对应货件标签。

准备前还必须确认：

- 货件组成和保质期已填入申请；
- 适用商品已完成“诚实标签”标记；
- 适用设备带唯一序列号或 IMEI。

### 商品标签

每件商品包装必须有：

- 俄文标签，最小 **40 × 25 毫米**；
- 与商品卡一致且可扫描的条码。

若原厂条码与商品卡不一致，应下载商品卡条码并覆盖原条码。不得用透明胶带覆盖条码。标签和条码应位于明显位置，且不得遮挡保质期和商品说明。

即使新增外包装是透明的，也必须在最外层重新粘贴商品条码和标签。

### 货件标签与拒收条件

货件标签必须贴在对应箱或托盘上，而不是直接贴在商品上。

- 托盘货件只需在托盘上贴货件标签；
- 运输货件同时需要每个箱的标签和托盘标签；
- 标签应平整、无折痕，推荐 A4，最小 120 × 75 毫米；
- 一个货件贴两张标签、多个货件使用同一标签、运输货件内箱子无标签，都可能被拒收。

项目装车前检查：

- `cargo_label_count = 1`；
- `cargo_label_id` 唯一；
- `label_target_cargo_id = actual_cargo_id`；
- 运输托盘内所有箱均有箱标签；
- 条码扫描测试通过。

### 保质期门槛

当前规则要求：

- 商品总保质期不少于 **120 天**；
- 交货时剩余保质期不少于 **90 天**；
- 已入库商品剩余保质期少于 **45 天**时，平台可下架并要求卖家取回。

这些数值应保存为动态策略并关联品类例外，不应视为所有未来商品永久统一阈值。

### 箱与托盘要求

| 项目 | 箱 | 托盘 |
|---|---|---|
| 单个重量上限 | 25 千克 | 商品总重 800 千克 |
| 数量 | 普通供应最多 30 箱；运输货件最多 1500 箱 | 最多 40 个 |
| 推荐/最大尺寸 | S 30×20×30、M 40×30×40、L 60×40×40、XL 60×80×50 厘米 | 含货物 120×80×220 厘米 |

托盘还应：

- 使用 120 × 80 × 14.5 厘米欧标托盘并带 EUR 标记；
- 符合 UIC 435-2 或 ГОСТ 9557-87；
- 商品摆放整齐并至少缠绕 3 层缠绕膜；
- 商品超出托盘边缘不超过 2 厘米；
- 重心稳定，运输中不会倾倒。

跨仓供应的箱子不得超出托盘边缘，并且同时满足交货点与最终仓的要求。

### 一致性与费用

实际货件数量必须与申请一致，否则供应可能被拒收。货件实际组成、后台货件组成和供应申请总组成必须三方一致。

若单个货件出现多货或少货，或货件组成与申请总组成不一致，平台会收取验收附加服务费。

推荐最终放行条件：

`实际总件数 = 货件申报总件数 = 供应申请总件数`

且：

`每个实际 cargo_id 的 SKU 数量 = 对应 cargo_id 的申报数量`

## 30. 官方页面级核验：送往交货点

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/bring-products-to-warehouse`
>
> 核验日期：2026-07-30

### 交货地点

日期、到达时间、交货点名称与地址以供应申请的“交货条件”为准。只有“填写数据”或“可交货”状态的申请才适合执行交货准备。

项目应在司机出发前生成不可变交货快照：

- `scheduled_arrival_at`；
- `dropoff_point_id/name/address`；
- `delivery_method`；
- `final_warehouse_id`；
- `snapshot_created_at`。

### 车辆要求

当前页面说明，特维尔 РФЦ 和特维尔枢纽不接收汽车列车。

托盘交货车辆应：

- 后部卸货；
- 卸货口宽度至少 2 米；
- 后挡板离地至少 110 厘米；
- 车门可打开 270 度；
- 地板适合电动叉车作业。

- 到场司机与申请登记司机不一致；

- 司机拒绝带走需取回且已存放超过 7 天的退货、残次或多货；
- 供应未处于可交货状态，例如未选时段；

## 31. 官方页面级核验：验收结果与异议

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/check-supply-status`
>
> 核验日期：2026-07-30

### 验收结果层级

平台提供：

- 单个货件报告：该货件进入“已接收”后可下载；
- 整笔供应报告：首个货件验收后开始生成，后续持续追加；
- 整笔供应验收单：全部验收完成后形成。

因此报告是渐进式数据，项目必须保存版本和生成时间，不能把首版报告误当最终结果。

跨仓商品若从计划到达日算起 90 天仍未送达最终仓，应联系支持。

### 文件处理路线

- 无 УПД-2 或“交货后上传 УПД 可选”：在后台确认验收单；
- “交货前必须上传 УПД”：在后台核对运单，并在 EDI 中确认差异文件；
- “交货后上传 УПД 可选”且需要 УПД-2：下载平台生成的 УПД-2，通过 EDI 签署发送。

“交货前 УПД”路线完成验收后，申请进入“完成”，约 1 天后进入归档；该路线不形成普通验收单和运单。

### 验收单内容

验收单包含：

- 状态、供应编号、计划日期和交货点；
- 申报数量、实际接收数量、差异、含税金额；
- 每个 SKU/货号的接收数、差异、未税单价、含税金额与增值税。

可能另行形成：

- 残次单：瑕疵或重量与随附文件不符；
- 多货单：找不到卖家有效商品卡的商品；错装型号按多货处理，正确型号按少货处理。

### 常见残次原因

- 缺少俄文标签；
- 缺少生产日期或保质期；
- 商品或包装变形、破损；
- 尺寸不符合仓储要求；
- 序列号/IMEI 缺失或错误；
- 已过期或剩余保质期不足；
- 无包装或包装不合规；
- 不满足温控或危险品储存条件；
- 冻坏；
- 空包装；
- 条码缺失或不可读；
- 属于仓库禁收危险品；
- “诚实标签”缺失、损坏或不可读。

### 接受、拒绝与自动确认

验收单、残次单和多货单需要在 **7 个日历日**内接受或拒绝，否则自动接受。

异议流程：

1. 下载并填写有理由异议模板；
2. 在每个有异议的文件页面单独点“拒绝”；
3. 上传模板；
4. 上传能证明交货的照片和视频；
5. 填写说明并提交。

若只拒绝验收单但接受残次/多货单，或后两者自动接受，则视为同意对应差异。若只接受验收单但未处理其他差异文件，申请不会进入“完成”；所有文件均需处理。

项目必须按文件独立建模：

- `act_id/type/status`；
- `review_deadline_at`；
- `auto_accept_at`；
- `accepted_or_rejected_at`；
- `objection_template_file`；
- `evidence_files[]`；
- `support_case_id`。

### 未接收商品取回

未接收商品出现在“取回与销毁”后，卖家应在 **5 天内**创建取回申请，否则可能自动销毁。

### 完成与后续争议

验收单确认后，即使存在差异，供应也可能进入“完成”；差异通过支持继续处理。拒绝验收单或差异单时，平台会自动创建支持请求。

完成、过期和拒绝的申请均进入归档，可下载历史文件和商品 XLS 复用于新申请。

## 32. 官方页面级核验：仓库、分拣中心与交货点

> 核验页面：`/libra/fbo/warehouses/adresa-skladov-fbo`
>
> 核验日期：2026-07-30

### 点位类型

- 履约仓：接收、拣选、包装、存储并向买家发货，也可处理卖家取回；部分仓另有“仅跨仓交货”系统名称；
- 分拣中心：处理跨仓供应并发往最终仓或配送中心；通常接收箱和托盘，但汉特-曼西斯克分拣中心当前只收箱；
- 自提/收货点：接收跨仓供应，只接收箱，不接收托盘；
- 某些点位另有“仅用于取回”的系统名称。

点位类型决定可接受货件类型、交货方式和取回能力。项目不能只按地址识别点位，必须保存官方系统名称与用途限定。

### 可用性优先级

官方明确建议，在创建供应申请时以后台实际可选点位为准。知识库地址清单仅用于参考，因为仓库负载、开放状态、交货路线和品类限制会变化。

优先级：

1. 当前申请返回的可选点位；
2. 点位实时状态与限制；
3. 官方地址页的最新资料；
4. 本地缓存。

缓存必须带 `verified_at` 和有效期。

### 点位数据模型

每个点位至少需要：

- `warehouse_id/guid`；
- `system_name`；
- `crossdock_system_name`；
- `pickup_only_system_name`；
- `point_type`；
- `cluster_id`；
- `physical_address`；
- `legal_consignee_address`；
- `coordinates`；
- `working_hours_by_operation`；
- `accepted_cargo_types`；
- `direct_supply_allowed`；
- `crossdock_allowed`；
- `return_pickup_allowed`；
- `tax_id/kpp/gln`；
- `dispatcher_phone`；
- `route_map_url`；
- `active_from/to`；
- `restrictions[]`。

### 动态限制示例

页面当前存在大量带日期的点位规则，例如：

- 某些仓关闭新供应或关闭跨仓预约；
- 多莫杰多沃跨仓当前只收托盘；
- 茹科夫斯基轮胎仓只接收未使用汽车轮胎；
- 阿斯塔纳特定“进口跨仓”系统点不可用于普通跨仓；
- 阿拉木图-2、阿斯塔纳作为跨仓最终点时必须填写货件组成。

这些示例证明点位限制是事件流，不应写成静态布尔值。建议：

- `restriction_type`；
- `effective_from/to`；
- `scope`：direct / crossdock / returns / category / cargo_type；
- `source_notice`；
- `observed_at`。

### 时段

仓库根据负载安排人员，卖家必须在申请所选时段到达。即使地址和营业时间允许，也不能把“仓库营业”解释为“任何时间均可交货”。

## 33. 官方页面级核验：配送集群

> 核验页面：`/libra/fbo/warehouses/table-klastery`
>
> 核验日期：2026-07-30

### 集群不是行政区

Ozon 将销售地理划分为集群，一个集群可跨多个联邦主体或覆盖整个国家。平台可以调整集群边界和组成，并承诺最晚提前 **5 个工作日**通知。

项目必须把集群建模为带生效区间的版本：

- `cluster_id`；
- `cluster_name`；
- `version`；
- `effective_from/to`；
- `member_regions[]`；
- `member_warehouses[]`；
- `notice_published_at`；
- `source_file_url`。

不得直接覆盖旧映射，否则历史销售、物流费用和供应建议会被错误重算。

### 两类集群

FBO 页面区分：

- 配送集群：影响配送速度和销售本地性；
- 区域系数集群：在远距离跨集群购买时可能提高买家看到的商品价格，但不影响卖家收入。

两个集群体系的边界和用途不同，项目不能复用同一字段。建议分别保存：

- `delivery_cluster_id`；
- `regional_coefficient_cluster_id`。

### 配送集群的业务影响

买家与发货仓在同一配送集群时：

- 通常配送更快；
- 销售本地性提高；
- 物流溢价更低。

平台有时会限制在卖家无库存集群中的销售。因此供货规划需要结合：

- 销售地理分析；
- 商品可用性；
- 集群库存；
- 本地性指标；
- 预计物流成本。

### 无供应仓的销售集群

当前页面说明，阿塞拜疆、格鲁吉亚、吉尔吉斯斯坦、土库曼斯坦和乌兹别克斯坦集群没有可供卖家供应的仓库。这不等于无法向当地销售，而是不能把它们作为普通 FBO 入仓目标。

### 当前版本

页面同时保留“自 2026-01-20 起”和“截至 2026-01-19”的集群结构，并提供新版 XLS。项目导入时应：

- 保存文件原始版本；
- 解析生效日期；
- 与当前数据库做差异；
- 在生效日前预生成迁移计划；
- 生效后按订单/供应业务时间选择正确版本。

## 36. 官方页面级核验：司机现场须知

> 核验页面：`/libra/fbo/warehouses/note-for-driver`
>
> 核验日期：2026-07-30

### 到场与卸货

司机到达后需要：

1. 领取通行证；
2. 出示护照和取货授权书，仓库可能复制文件；
3. 确认具体泊位并服从现场指引；
4. 卸货前熄火、拉手刹并放置车轮止退器。

禁止携带动物、爆炸品、毒品、危险化学/有毒物质、枪械/冷兵器和喷雾器进入。

- 场内最高速度 10 千米/小时；
- 只可停在有标线的允许区域，否则可能被拖走；
- 故障车辆应拖离，不得场内维修；
- 交货后 30 分钟内离场。

### 场内行为

禁止维修或清洗车辆、乱扔垃圾、非指定区域吸烟、明火、饮酒、拍照录像、排放废物或处于酒精/毒品影响状态。

页面禁止现场拍照录像与验收异议要求上传交货照片/视频并不等于冲突：证据采集必须在允许区域和允许时点完成，不能擅自在仓库受限区域拍摄。

### 卸货责任与车辆参数

- 车辆后挡板离地至少 110 厘米；
- 托盘货件最高 2.2 米；
- 托盘不得叠放，箱子可以叠放；
- 在分拣中心和履约仓：卖家/司机卸箱，Ozon 卸托盘；
- 在自提/收货点：卖家/司机卸箱，不接收托盘；
- 分拣中心不核对纸质文件；
- 自提/收货点不签纸质运单。

项目应生成司机版交货清单，并记录司机已确认：

- 点位规则；
- 车辆适配性；
- 卸货责任；
- 随车文件；
- 是否有需取回商品；
- 场内行为规则。

## 38. 官方页面级核验：仓储费用

> 核验页面：`/libra/fbo/warehouses/warehousing-cost`
>
> 核验日期：2026-07-30

### 免费与付费库存

仓储分为：

- 付费：像其他服务一样从卖家余额扣除；
- 免费：仓储折扣 100%，可能来自促销、优惠品类或供应的免费仓储天数。

品类和商品类型对应不同费率与免费天数。免费期结束后，按商品体积的每升每天计费。

费率、免费期和优惠范围全部属于动态规则，执行前必须核对官方“佣金与费率”。

### 免费天数的分配

免费天数按新供应产生，但作用于同一 SKU 的商品并可跨仓使用：

- 各供应产生的免费额度累加；
- 优先消耗较早供应的免费天数；
- 早期商品售出后，未消耗额度可转给同 SKU 剩余商品。

因此免费仓储不是“某一物理件永久绑定某一供应”的简单属性，而是 `SKU + 到期日 + 可免费件数` 的额度池。

建议数据模型：

- `sku`；
- `source_supply_id`；
- `free_units_granted`；
- `free_period_end`；
- `remaining_free_unit_days`；
- `allocation_priority`；
- `warehouse_type_rate`；
- `paid_volume_liters`；
- `daily_charge`。

### 费用页面与预测

后台展示：

- 当前月已计费用；
- 按现有销售与补货节奏推算的月末费用；
- 未来 28 天费用预测；
- 每个 SKU 的付费/免费件数与升数；
- 最近 28 天仓储费用；
- 仓储费用占订单金额比例；
- 免费期开始转付费日期；
- 库存可售天数 IDC；
- 商品访问、转化和价格指数。

预测基于库存不变或现有销售/补货趋势，不是账单承诺。项目需保存预测生成时点和假设。

### 四类优化建议

- 访问量低：推广或参加活动；
- 价格指数不利：优化价格；
- 加购转化低：优化商品与销售条件；
- 建议取回：慢销且付费库存过多。

“即将转付费”关注未来 14 天，“将转付费”展示未来 28 天内最近三批开始计费日期和数量。

### 两类导出报告

- 按供应：免费天数的产生、消耗、到期及每个供应/每个 SKU 的免费件数；可导出当前或未来月份；
- 按商品：每日、每仓、每 SKU 的已计费用、总体积毫升、付费件数与总库存。

导出期间必须在一个自然月内。

## 39. 官方页面级核验：仓储费用报告问答

> 核验页面：`/libra/fbo/warehouses/voprosy-i-otvety-po-otchtu-o-stoimosti-razmeshcheniya`
>
> 核验日期：2026-07-30

### “开始付费仓储”的含义

该字段显示最早一批供应的免费期结束日期和剩余天数，因为免费额度先用于早期供应商品。

如果同一 SKU 已有部分商品付费，页面可能不再显示单一开始日期；应查看供应报告中的额度分层。

### 季节性商品

由于技术限制，页面和报告可能仍显示季节性商品的付费开始日期与费用预测，但实际不收费。应以每日“已扣款”字段为准。

项目需要区分：

- `projected_charge`；
- `billable_under_policy`；
- `actual_charged_amount`。

### 跨供应与跨仓

同一 SKU 的免费额度可以：

- 由不同供应累加；
- 作用于历史供应的同 SKU；
- 跨不同仓使用。

仓储费率仍可能随仓库类型不同。出库顺序与计费额度消耗顺序也可能不同：平台为加快配送可从近仓发货，但计费时仍优先消耗早期供应对应额度。

### 判断未来付费量

未来某日：

`付费件数 = max(0, 预计库存件数 - 当日可免费件数)`

官方供应报告的未来计算不预测销量导致的库存变化，因此这是静态库存情景，不是精确账单。

### 报告缺失与技术值

- 2024-10-01 及以前的供应可能缺供应编号；
- 2024-10-17 以前的供应可能缺仓库；
- 多货、错装或内部仓储操作产生的商品也可能无物理供应编号/仓库来源；
- 免费期已结束的商品不会出现在“按供应”免费期报告；
- 无库存但仍有免费额度的 SKU 仍可能出现；
- `999999` 是历史升数奖励免费仓储的技术占位值，用于把费用归零，不代表真实天数。

项目导入报告时必须把这些情况标记为 `known_legacy_gap` 或 `technical_sentinel`，不能当作脏数据直接删除。

## 40. 官方页面级核验：Ozon 仓间调拨

> 核验页面：`/libra/fbo/rabota-so-stokom/peremeshchenie-tovara-mejdu-skladami-ozon`
>
> 核验日期：2026-07-30

### 用途与准入

仓间调拨用于：

- 把商品转到需求更高的集群；
- 提高销售本地性；
- 把商品集中到一个仓后统一取回。

调拨期间：

- 商品被预留后不可销售；
- 不收仓储费；
- 不消耗免费仓储天数。

项目必须把调拨在途库存从可售库存扣除，但仍纳入资产与履约追踪。

申请创建后立即进入平台处理，不能编辑或取消。创建前应进行最终确认，保存：

- 发货仓、收货仓和数量；
- 预计时间；
- 预估费用；
- 预计 28 天销售增量；
- 最低数量校验；
- 用户确认时间。

### 调拨状态

建议映射：

| 官方状态 | 项目状态 |

| 创建 | `created` |

商品实际到达目标仓时，平台才按整个货件中的商品计收调拨费。金额必须动态查询官方费率。

自创建调拨超过 **60 天**仍未到达目标仓时，卖家可请求商品和服务费赔偿。平台说明在申诉获批后 45 天内补偿。

### 推荐逻辑

平台建议：

- 目标集群库存不足 28 天时补入；
- 来源集群调出后不应低于 30 天库存；
- 不向商品属于慢销的目标集群推荐；
- 只推荐可用且无商品准入限制的方向；
- 每个商品可有多个目标集群。

推荐未考虑：

- 具体发货仓和收货仓；
- 指定仓实际库存；
- 自定义天数，只按 28 天；
- 自定义数量的费用；
- 尚在途供应；
- 最低调拨数量。

推荐最多每月发送一次，下载链接有效 2 周。

## 41. 官方页面级核验：慢销商品

>
> 核验日期：2026-07-30

### 定义

只对 Ozon 仓内有可售库存的 SKU 判断慢销。满足任一条件：

- 超过 28 天无销售；
- 可售库存预计超过 120 天。

销量按该 SKU 在所有 Ozon 仓的销售汇总。

排除：

- Super 商品；
- 季节性商品；
- 首次上架不满 28 天的新品。

慢销相关状态：

- 过量；
- 无销售；
- 无销售、受限。

- `days_without_sales`；
- `days_of_supply`；
- `liquidity_status`；
- `is_super_product`；
- `is_seasonal`；
- `first_available_at`；
- `replenishment_restricted`。

1. 参加库存清仓或其他库存折扣活动；
2. 创建卖家自有活动，可限定仓库地理范围；
3. 使用商品推广；
4. 调拨到有需求集群；
5. 从仓库取回，用其他渠道销售。

活动叠加折扣过高时，商品可能进入价格隔离，暂停售卖。因此清仓动作必须做最终售价与利润校验。

创建供应申请时，平台会显示慢销商品数量并允许下载清单或一键移除。项目应在提交前提供同等检查，默认建议移除，但不能未经用户确认自动删除。

## 42. 官方页面级核验：Super 商品与 Super 供应

> 核验页面：`/libra/fbo/rabota-so-stokom/super-tovary`
>
> 核验日期：2026-07-30

### Super 商品

当前 Super 标识只授予新品，不再使用中位价格和日均销量作为判断条件。

商品首次进入 Ozon 仓后，通常在验收完成 24 小时内获得“新品”标识，标识持续 28 天。可在商品可用性和库存管理中查看。

### Super 供应

- 仅俄罗斯卖家可用；
- 一笔供应中 Super 商品件数占比必须 **超过 90%**；
- 按商品总件数计算，不按不同 SKU 数计算；
- 不同交货方式分别创建申请并独立判断。

判定公式：

`super_ratio = Super 商品件数 ÷ 供应总件数`

只有 `super_ratio > 0.90` 才是 Super 供应。

交货时若比例下降到 90% 或以下，平台可能补收多货处理费和跨仓费。因此项目要同时保存创建时和交货时比例。

### 当前权益

- 跨仓费 100% 折扣：自提点、分拣中心或仓库交货时覆盖整个服务；快递员上门时只覆盖交货点到最终仓的运输；
- 加速仓库验收；
- 提供更多交货时段。

这些权益不适用于 Ozon Fresh 暗仓，且属于动态优惠，必须核验最新页面和费率。

### 编辑

编辑后仍需保持超过 90%。如果原时段已不可用，修改不能保存，需要重建申请。

建议字段：

- `is_new_product`；
- `new_product_badge_from/to`；
- `super_units`；
- `total_units`；
- `super_ratio_at_creation`；
- `super_ratio_at_dispatch`；
- `super_benefits_applied[]`；
- `benefits_reversed`；
- `surcharge_reason`。

## 44. 官方页面级核验：通过 EDI 形成并发送 UPD-2

> 核验页面：`/libra/fbo/documents/hand-in-UPD-2`
>
> 核验日期：2026-07-30

### 适用范围与上传时点

不是每一笔 FBO 供应都按同一种方式提交 UPD-2。当前官方规则至少区分：

- 普通商品送往暗仓或 `Павловская Слобода РФЦ Негабарит`：供应前必须提交；
- 珠宝：供应前必须提交，并补充规格编号；
- 受「Меркурий」认证约束的商品：供应前必须提交；若与普通商品混装，同一申请中的全部商品都要进入 UPD；
- 「Честный знак」标记商品：按申请采用的“供应前”或“供应后”方案处理；供应后方案中，若存在标记商品，建议在确认验收单后 3 日内发送；
- 标记商品送往阿斯塔纳、阿拉木图-2、明斯克相关仓：供应前必须提交。

卖家可为**新申请**选择三种方案：

1. 所有申请均在供应前强制上传；
2. 仅当申请含「Честный знак」商品时，在供应前对申请内全部商品强制上传；
3. 供应后可选上传。

方案修改只作用于新申请。珠宝、`Меркурий` 商品、上述指定境外仓和大件仓等特殊场景会被平台强制切换到供应前上传。

项目不能用一个全局布尔值表示 UPD 要求，应至少保存：

- `upd_scheme`；
- `upd_required`；
- `upd_required_reason`；
- `upd_due_stage`；
- `upd_due_at`；
- `upd_status`；
- `acceptance_act_confirmed_at`。

### 文件形成与核心字段

可在 EDI 中手工创建，也可从卖家后台供应申请生成 XML。核心校验包括：

- 供应申请号；
- 商品 SKU；
- 单据编号；
- 单据日期；
- 发货人与法定地址；
- 签署人职务和姓名；
- 珠宝规格编号；
- 可追溯商品的原产国和批次号。

单据日期不得晚于发运日。通过后台模板生成时，日期还应与发运日在同一个月且不晚于发运日。商品按 SKU 接收；供应前方案通常与供应申请核对，供应后方案通常与验收单核对。

标记码不会在所有供应前模板中自动补齐，卖家需按商品类别补充。一个 UPD/UKD 的同一 SKU 不得混用逐件追溯和按品种数量追溯。

### EDI 发送与平台验签

- 官方直接对接 `Контур.Диадок` 与 `Сфера Документы（СберКорус）`；其他服务商需确认可通过漫游互通；
- 接收方为 ООО «Интернет решения»（ИНН `7704217370` / КПП `997750001`）；
- 建议直接上传后台生成的 XML，避免手工修改后与申请或验收单不一致；
- 在「Контур.Диадок」中选择 `ОСЛ（Отдел Складской Логистики）` 或总部门；
- 正确发送后，单据通常在数分钟内出现在卖家后台。

平台自动签署的前提：

- 供应前 UPD 与申请完全一致，并在商品全部验收入仓后签署；
- 供应后 UPD 与已确认验收单一致。

关键状态包括：

- `В УПД нет части товаров из поставки`：UPD 缺少申请中的部分商品；
- `Загружены с ошибками`：已上传但存在错误；
- `Загружены в ЭДО`：已进入 EDI。

强制供应前上传时，必须同时满足 UPD 为“已进入 EDI”且供应为“可发运”，否则仓库不接收。

### 错误修复与责任

修复流程是：

1. 在 EDI 中作废错误单据；
2. 修正内容；若某些标记码无法投入流通，可删除这些码，但不得改变商品总数量；
3. 使用**同一个单据编号**重新上传和发送；
4. 通过漫游且非 `Контур.Диадок`/`Корус` 的服务商，作废后还需按官方路径联系支持并提供作废单据号。

不要以新编号发送、不要用更正/调整单替代重新上传，也不要把 UKD 当成 UPD-2。否则平台可能无法签署或接收供应。

标记商品信息与状态正确性的责任归卖家。若平台因卖家未正确传递标记信息而受罚，可从卖家收益中扣除。项目应把“确认验收单后 3 日”作为标记商品的动态截止提醒，并保留发送、签署、作废和重传审计轨迹。

### 可追溯商品

当前页面说明：RNPT 暂不要求常规主动提交；若企业买家需要，Ozon 会另行索取。需要提交时，XML 文件名使用 `PROS` 属性并填写追溯批次、计量单位和数量等字段，或在相应列填写原产国与追溯批次。

这属于动态税务和追溯规则，项目只能记录官方当前状态，实际执行前必须再次核对。

## 45. 官方页面级核验：运输单据

> 核验页面：`/libra/fbo/documents/logistics-docs`
>
> 核验日期：2026-07-30

### 是否必须

FBO 供应通常可不带随附单据，但 Ozon 可在以下场景签署运输单据：

- 物流公司或卖家内部报账需要；
- 交接供应中的多货或瑕疵品，并在单据中注明退回数量；
- 从卖家仓向 FBO 上门取货司机交货；
- 后续争议处理需要证据。

商品运输单、商品出库单或 UPD-1 不能替代运输单据，因为这些单据可能表示所有权转移给 Ozon，与平台合同关系不符。

### 上门取货场景

同一天交给司机、来自多笔申请的商品，平台会形成一份合并运输单据。申请达到“可发运”后，在供应申请页下载 PDF：

- 打印 4 份：卖家留 1 份，司机带 3 份；
- 检查平台预填的发货人、收货人等信息；
- 补齐第 7、8 项；若使用运输货位，填写运输货位数，而不是申请内全部纸箱数；
- 卖家签字；有公章时加盖公章。

### 仓库签署

文件交给司机。使用第三方运输公司时，将文件装入透明防水袋，标记“Документы”，并贴在某个外箱外侧。司机在仓库把文件交给调度处。

仓库签署前会核对：

- 货位数量；
- 实际交货仓信息；
- 供应日期；
- 供应申请号。

项目建议把运输单据建模为可选但可审计的交接凭证：

- `transport_waybill_required_reason`；
- `waybill_group_key`（同日多申请合并）；
- `cargo_place_count`；
- `copies_printed`；
- `seller_signed_at`；
- `warehouse_signed_at`；
- `document_attached_to_cargo`；
- `dispute_evidence_id`。

## 46. 官方页面级核验：UPD 与 EDI 常见错误

> 核验页面：`/libra/fbo/documents/errors-upd-edo`
>
> 页面标注更新：2026-07-14
>
> 核验日期：2026-07-30

官方错误表按四类供应组织：

1. 强制标记商品；
2. 强制标记的珠宝；
3. 强制兽医认证商品；
4. 无 EDI 供应。

### 标记商品

主要校验维度包括：

- 标记码是否处于“流通中”，而不是仅生成或签发；
- 商品条码与标记码 GTIN 是否一致；
- 标记码数量与需标记商品数量是否一致；
- 需要标记的商品是否缺少标记码；
- 商品卡上的标记属性是否与 UPD 内容一致；
- 逐件或按品种数量追溯格式是否符合该类目要求；
- UPD 中的标记码是否与验收单实际接收的标记码一致；
- 是否误用运输包装聚合码。

典型修复动作是先修正商品卡、`Честный знак` 状态或标记码集合，再作废错误 UPD 并重新上传。项目应在提交前执行同等校验，特别是：

`GTIN ↔ 商品条码 ↔ SKU ↔ 标记属性 ↔ KIZ 数量 ↔ 验收单`

### 珠宝

除普通标记校验外，还要核对：

- ГИИС ДМДК 规格中的含税总价与 UPD 含税总价；
- 规格中的增值税总额与 UPD；
- 规格不能仍处于草稿；
- 规格编号不得含西里尔字符或多余符号；
- UPD 必须填写规格编号；
- 卖家银行账号、BIC、银行名称；
- 供应依据单据号；
- 发货人/卖家、收货人/买家的 INN；
- 商品 ID 或 GTIN；
- 商品是否确属珠宝类目。

这是类目特有规则。当前项目不经营珠宝时，应保留为知识而不构建专用操作流；若未来经营，再启用专用验证器。

### `Меркурий` 兽医认证商品

常见错误是：

- 指定仓不接受重量商品，数量却不是整数；
- 兽医单据的交易类型不符合与 ООО «Интернет решения» 的合同关系；
- эВСД 中的 GTIN 不正确；
- 应收到的 эВСД 未从 `Меркурий` 系统到达。

修复时应通过 `Меркурий` 发送交易类型、GTIN 和关联关系正确的 эВСД；数量不符合仓库规则时，作废 UPD 并按正确整数重新上传。

### 无 EDI 供应与验收单一致性

供应后 UPD 的权威对照物是验收单。以下字段必须一致：

- 卖家、买家、收货人的 INN/KPP；
- 买家和收货人地址及国家代码；
- 商品集合和 Ozon ID；
- 数量、单价、未税金额、税率、税额、含税金额、消费税；
- 计量单位；
- 各类汇总金额。

国家代码俄罗斯为 `643`。若 UPD 中存在验收单没有的商品，必须删除。若验收单尚未被卖家接受，应等待其状态变化，不要重复发送 UPD。

相同编号和日期的 UPD 在一个日历年内不能重复；如果已由双方签署，相关提示只是信息提示，无需处理。UPD 中也不应包含不适用的更正日期或支付结算单据字段。

### 项目错误模型

不要只保存一段不可查询的错误文本。建议标准化为：

- `error_domain`：marking / jewelry / mercury / acceptance；
- `error_code_or_text`；
- `line_number`；
- `expected_value`；
- `actual_value`；
- `source_record_id`；
- `remediation`；
- `requires_voiding`；
- `requires_support`；
- `resolved_at`；
- `resubmitted_document_id`。

## 47. 官方页面级核验：面向企业买家的海关申报号

> 核验页面：`/libra/fbo/documents/upload-gtd`
>
> 核验日期：2026-07-30

### 何时适用

ГТД（货物海关申报）用于证明进口商品合法跨境运输，包含货物、运输工具、海关价值、发货人与收货人等信息。

当前页面说明：除俄罗斯、白俄罗斯、哈萨克斯坦、亚美尼亚、吉尔吉斯斯坦和乌兹别克斯坦外，从其他国家进口的商品需要相关申报信息；卖家自己生产的商品不需要。

在 FBO 供应申请或 UPD-2 中预先填写 ГТД 号不是入仓硬门槛，仓库可在没有该号码时接收。若企业买家为了进项增值税返还而请求，Ozon 会联系卖家索取。官方仍建议预填，以减少买家等待。

### 号码来源与格式

号码来自：

- 卖家进口时取得的海关申报；
- 已完成清关的上游供应商。

模板格式要求：

- 最多 29 个字符；
- 只能包含数字和 `/`；
- 不得包含字母、句点、逗号或国家名称；
- 一个单元格只能有一个申报号；
- 同一商品对应多个申报号时不要全部塞入一个单元格，当前页面建议留空并等待平台按需索取；
- 俄罗斯商品的 ГТД 字段留空。

### 上传流程

在 `FBO → 供应申请 → 供应准备` 中打开申请：

1. 选择“上传 ГТД”；
2. 下载 XLSX 模板；
3. 填写按 ОКСМ 表示的原产国代码；商品卡已有生产国时平台可能自动预填；
4. 填写海关申报号；
5. 保存并上传。

上传后的文件本身不在后台展示，但平台会显示成功提示并改变申请状态。文件有误时可再次上传。

项目数据至少应区分：

- `origin_country_code`；
- `is_self_manufactured`；
- `customs_declaration_number`；
- `customs_number_valid`；
- `customs_number_source`；
- `customs_uploaded_at`；
- `customs_upload_status`；
- `requested_by_b2b_buyer_at`。

这里的“申报信息适用国家”和税务用途可能变化，实际交易前必须核对当前官方与税务规则。

## 48. 官方页面级核验：FBO 模式与适用边界

> 核验页面：`/libra/fbo/scheme-of-work/about`
>
> 核验日期：2026-07-30

### 模式职责

FBO 是卖家把商品预先送入 Ozon 履约仓的模式。入仓后，Ozon 负责：

- 计算卖家和买家的配送时效与费用；
- 仓间及末端运输并更新状态；
- 通过自提点、智能柜或快递交付；
- 接收买家退货。

卖家仍负责商品、合规、供应申请、入仓前准备、补货、库存质量和财务核对。

### 适用对象

当前页面将 FBO 描述为适合：

- 法人或个体工商户；
- 没有自有仓配能力的卖家；
- 需要覆盖俄罗斯及部分周边国家的业务；
- 需求相对稳定、适合预先备货的商品；
- 通常不超过 80 kg 的商品；特定大件仓上限可到 120 kg。

重量、品类禁限售、仓可用性和跨境覆盖均属于动态规则，创建供应前应实时核验。虽然平台允许同一后台同时使用 FBO、FBS、realFBS，本项目按用户决策只建设 FBO，不因官方允许混用而扩展 FBS/rFBS 操作能力。

### 完整链路

官方基础流程是：

`创建供应申请 → 选择集群与商品 → 选择自送/跨仓/上门取货 → 选择日期时段 → 准备货件 → 发运 → 跟踪 → 仓库验收 → 上架与补货`

Ozon 决定消费者订单的配送地理范围，并可能把商品配送至俄罗斯、部分欧亚经济联盟国家及其他周边国家。若商品进入欧亚经济联盟相关国家，页面提示卖家通常需在次月第 10 个工作日前向俄罗斯联邦海关提交统计表；这是动态税务义务，执行前必须核对最新规则。

### 到付订单

部分适合试穿或验货的类目会自动开放“收货后付款”，例如珠宝、服装、鞋类及部分配饰。当前页面同时列出重量、体积、部分敏感类目和 Economy 商品等限制。

关键边界：

- 由平台按商品和买家条件自动决定；
- 卖家不能关闭；
- 买家额度与历史购买、金额和签收率相关；
- 卖家仍按普通结算周期收款。

项目应把它视为订单支付属性，而不是卖家可配置开关：

- `pay_on_receipt_eligible`；
- `pay_on_receipt_reason`；
- `buyer_pay_on_receipt_limit`（若官方数据可得）；
- `payment_collected_at_delivery`；
- `settlement_schedule`。

## 49. 官方页面级核验：FBO 高频问答

> 核验页面：`/libra/fbo/scheme-of-work/vopros-otvet-fbo`
>
> 核验日期：2026-07-30

该页是跨流程问答，不替代各专题正文。以下为新增或值得形成操作规则的要点。

### 供应、跨仓和验收争议

- 跨仓申请必须填写货位数量、货位内商品组成和有保质期商品的保质期，否则可能产生额外验收费；
- 跨仓费取决于交货点类型、线路和货位体积，创建申请时锁定价格，商品抵达目的地后才收费；
- 页面当前给出的跨仓总容积上限为 100,000 L，托盘不超过 800 kg，纸箱不超过 25 kg；
- 使用 UPD 的供应，通过 EDI 驳回 UPD-2 并提交异议材料；无 UPD 供应驳回验收单后，系统自动建立支持工单；
- 一次统一发运产生的每个子供应，验收单及瑕疵/多货单都要分别在 5 日内确认或争议，否则平台自动确认；
- 验收单价格采用验收日商品卡折后价；赔付计算可能使用实际计算日折后价。

项目必须把“统一发运”与“子供应验收”分层，不能只在父级保存一个确认状态。

### UPD 补充判断

- 手工填写时，日期来自验收单或更早，商品组成来自供应申请，税率来自商品卡，价格来自商品卡折后价；
- 内部核算需要时，UPD 价格可低于商品卡价格，但不能高于验收单价格；
- `ID товара` 填商品 SKU；
- 宣告价值来自 UPD-2，简化模式则来自验收单，用于丢失或损坏赔付；
- UPD 与验收单的收货地址必须一致；
- 未确认验收单或字段不一致时，平台不会自动签署。

### 到仓操作

- 当天轻微迟到可能进入现场排队；严重迟到或现场繁忙时可拒收，需改约；
- 同一车辆可运输多笔供应，但必须物理清晰分隔；
- 托盘只能在发运当天、卸空后取回；离场后、跨仓供应或非欧标托盘通常不退。

### ПВЗ 与 ППЗ 交货

页面当前规则：

- 二者均可作为跨仓交货点；
- 每笔最多 30 箱、单箱不超过 20 kg；
- ПВЗ 总容积通常不超过 1,000 L，部分点为 500 L；ППЗ 不超过 1,000 L；
- 强制标记/UPD 商品不能交 ПВЗ，可交 ППЗ；
- 未填写货位组成和保质期时，ПВЗ 会拒收，ППЗ 可接收但可能收费；
- 汽车信息只在 ППЗ 场景需要；若不驾车进入，可填写联系人；
- 当前页面最后时段为 19:00–20:00。

这些阈值和时段均为动态规则，提交申请时应从实时交货点能力读取。

### 在途、验收和订单

- 预计抵仓时间在供应申请的货位或发运页查看；
- 超期应按直送或跨仓路径联系支持，并只提供供应号；
- 当前页面说明，申请进入“仓库验收”后通常需要 2–5 个工作日完成数量与质量检查；
- FBO 商品可见性不能由卖家像 FBS 那样切换；
- 同时存在 FBO/FBS 库存时，平台按买家集群和距离选仓；同集群时优先 FBO；
- 买家可自己选择快递日期，因此订单可能长时间停留在“等待拣货”；
- Ozon 可基于竞品库存、仓容量、区域需求和买家活跃度自动跨仓调拨；
- 买家取消后的商品通常约 10 日回到邻近仓，页面给出的最长时间为 60 日。

### 折价与销毁

- 轻微外观或包装缺陷的退货可折价重新销售；重大缺陷要求卖家取回；
- 折价由卖家承担，平台按状态决定折扣；卖家可调整折扣或选择取回；
- 供应中的瑕疵和多货出现后，卖家有 5 日创建取回申请，否则自动进入销毁；
- 创建取回申请后，自提通常需在 30 日内完成，平台快递取回可到 65 日；
- 错过库存退货取回时段后通常还有 14 日；
- Ozon 快递两次无法交付退货后，可能不再允许取回；
- 只有因包装不当受损且连折价销售都不可能的商品才按该原因销毁；
- 销毁由认证合作方执行并产生证明文件。

建议任务模型：

- `return_or_disposal_reason`；
- `decision_due_at`；
- `pickup_due_at`；
- `courier_delivery_due_at`；
- `auto_disposal_at`；
- `disposal_partner_document_id`；
- `markdown_discount_rate`；
- `seller_discount_adjustment`；
- `pickup_eligibility_status`。

### 移动端能力边界

移动端每次只能为一个集群创建供应申请。移动端创建的申请进入“填写数据”状态后，会出现在网页版 `FBO → 供应申请`。

- 跟踪仓库验收；
- 必要时编辑或删除申请。

- `created_via = mobile | web | api`；

- `labels_ready`；

## 52. 官方页面级核验：货位与保质期问答

> 核验页面：`/libra/fbo/gruzomesta-i-podgotovka-k-otgruzke/voprosy-i-otvety-o-gruzomestah-i-srokah-godnosti`
>
> 页面标注更新：2026-05-18
>
> 核验日期：2026-07-30

### 托盘、纸箱和运输货位

- 普通供应把托盘声明为货位时，只填写托盘内商品组成，标签也贴在托盘上；
- 若能精确填写托盘上每个纸箱的组成，可使用“运输货位”：托盘贴运输货位标签，每个箱贴纸箱标签；
- 使用运输货位可把托盘上的纸箱上限提高到 1,500 箱；
- 当前页面说明，普通供应每笔最多 30 箱或 40 托盘；运输货位场景最多 1,500 箱；
- ПВЗ/ППЗ 只接收纸箱，分拣中心和履约仓可接收托盘或纸箱；
- 一个货位可填写 1 到 1,000,000 件商品，但一笔申请总体积不超过 100,000 L。

这些阈值可能变化，应在申请提交时按交货点实时校验。

### 修改截止

货位商品组成最晚可在以下时间修改：

- 自送仓库、ПВЗ 或分拣中心：时段开始前 1 小时；
- Ozon 上门取货：提前 2 日。

错过时段时，应先在 2 日内改约，再修改供应商品组成，并同步更新货位组成。发运后不能再改货位数量或商品组成。

### 单货位、混合货位与存放区

- 单货位：只含同一 SKU，数量不限于一件；
- 混合货位：含多个 SKU；
- 为避免验收分拣费，建议把同一存放区的商品放进同一货位。

项目校验不能把“单货位”误解为“单件商品”，也要在申请商品组成变化后重新验证所有货位。

### 保质期

- 商品类目要求保质期时必须填写；
- 平台发现保质期错误时可能收取处理费；
- 同一货位内商品必须具有相同保质期，不同保质期应拆分货位；
- 当前页面给出的入仓条件：总保质期不少于 120 日，剩余保质期不少于 90 日；
- 剩余不足 45 日时，平台会下架并要求卖家取回。

保质期属于强动态、强类目规则。项目应同时保留：

- `manufactured_at`；
- `expires_at`；

### 服务与计费

跨仓是卖家把供应送到方便的接收点，再由 Ozon 运至最终履约仓的付费服务。统一发运和 Ozon 上门取货也可能包含跨仓环节。

费用取决于：

- 交货点类型；
- 货位体积；
- 起终点物流方向。

后台显示预估费用；若实际货位与申报一致，费用应与预估一致，否则按验收事实重新计算。费用在商品到达目的仓后收取，可在财务余额和店铺经济页面核对。

- 一般车辆后车板距地面至少 0.8 m，部分分拣中心有 0.9、1.1 或 1.2 m 的特殊要求；

## 54. 官方页面级核验：「Честный знак」标记商品

### 判断与责任

服装、鞋、药品、香水等多个类目需要国家追踪标记，完整类目清单动态变化。Ozon 主要依据商品卡的 TN VED 判断，因此卖家必须正确填写 TN VED、必要时填写 OKPD2、GTIN 和“需要标记码”属性。

每个需标记商品应满足：

- 具有可扫描的 Data Matrix，而不是普通 QR；

- `tn_ved`、`okpd2`、`gtin`；
- `marking_required` 与判定来源；
- `marking_code`；
- `marking_format`；
- `marking_status`；
- `owner_before_supply`；
- `label_readable`；
- `category_format_valid`；
- `verified_at`。

- 大多数标记商品可先入仓，再在确认验收单后发送 UPD-2；
- 包装饮用水需供应前发送；
- 供应后方案可把标记与普通商品混装；

如果申请错误标成需/无需标记，应先核对 TN VED，再向支持提交申请商品 XLSX 和合规证明。已有申请的显示可能不会立即纠正，但平台会按最终判定验收。

### 异常状态、取回与报表

- “未投入流通”：在「Честный знак」改为“已投入流通”后重发 UPD；
- “已退出流通”：若退出发生在验收日前，先恢复流通；若发生在验收后，按官方指导从 UPD 删除不应出现的代码；

- 未识别或无法扫描的商品按供应取回，已入仓但不能恢复状态的商品按库存取回；
- 库存取回不能指定精确标记码，平台准备所有未进入销售的同类商品；
- 标记商品销售报表可从订单分析中下载。

包装饮用水的按品种数量追溯 UPD 需使用 `MARK` 属性，并在 `<НомУпак>` 中填写 GTIN 和包装内数量。兽医认证商品还需在 `Меркурий` 形成电子兽医随附单据。

## 55. 官方页面级核验：通过 UKD 返还标记码

> 核验页面：`/libra/fbo/markirovka-tovarov/ukd`
>
> 核验日期：2026-07-30

### 适用条件

UKD（通用更正单据）只用于**供应前提交 UPD-2**的卖家。当 UPD-2 已把标记码转给 Ozon，但仓库因缺货、瑕疵、多货或代码不一致只接受部分商品时，卖家需通过 UKD 把未接收商品的代码转回自己名下。

供应后生成 UPD-2 时，验收单和 UPD 已按实际接收数量形成，不需要这条返还流程。

### 正确流程

1. 在 EDI 中接收并签署 XML 格式 TORG-2 差异单；
2. 原始 TORG-2 中，“按单据”是供应前 UPD 的全部代码，“实际”是仓库接收代码，“短缺”是未接收代码；
3. 以已签署 UPD 和 TORG-2 形成 UKD；
4. UKD 的“之前”填写 UPD 中全部代码，“之后”只填写 TORG-2 实际接收代码；
5. 在 5 个工作日内通过 EDI 发送；
6. Ozon 核对供应已关闭、UPD 已签署、验收单和 TORG-2 存在并有效；
7. Ozon 签署后，EDI 服务商把返还代码传至「Честный знак」，代码回到卖家余额；
8. 卖家另行取回未接收商品。

### 核心校验

UKD 必须同时与 UPD、TORG-2 和供应申请一致：

- 关联 UPD 已由 Ozon 签署；
- 存在卖家已签署的 TORG-2；
- 供应申请号正确；
- 卖家/买家 INN、KPP、地址和国家代码正确；
- 商品集合只能来自关联 UPD 和 TORG-2；
- “之前”的数量、计量单位、单价、未税金额、税率、税额、含税金额与 UPD 一致；
- “之后”数量等于供应商单据数量扣除 TORG-2 瑕疵/短缺后的结果；
- “之后”金额按数量和单价重新计算；
- “之前”代码等于 UPD 代码；
- “之后”代码等于 TORG-2“实际”代码，不能包含瑕疵商品代码；
- 俄罗斯国家代码为 `643`；
- 不接受填写“更正编号/日期”的修正版 UKD。

错误单据通常需作废后重新形成并发送；字段看似正确但平台仍报错时，按官方 UKD 支持路径提交。

## 57. 大件商品（KGT）：FBO 适用性与经营闭环

KGT 不是单纯的商品标签。它同时改变商品可接收仓点、供货预约、车辆和装卸条件、包装/托盘、储存占用、正反向物流成本以及退货处置。不能只根据商品类目判断，也不能把 2023 年视频或其他模式的历史重量阈值套到当前 FBO。

### FBO 上架前检查

1. **成品包装后的尺寸与重量**：记录长、宽、高、实际重量、测量时间和证据照片；裸品数据不能代替计费/验收数据。
2. **平台分类结果**：保存普通件/KGT 等平台识别及其规则版本；本地计算只做预警，平台结果为业务事实。

5. **车辆与预约**：核对车型、车厢、进场条件、装卸责任和时间窗口；KGT 的现场失败成本显著高于小件。
6. **单位经济**：同时估算销售佣金、入仓运输、装卸、仓储占用、正向物流、末端交付、拒收/退货、取回和处置。
7. **售后可逆性**：提前确认退货去向、可否重新上架、返运成本、损坏责任与证据要求。

> Ozon 大学入口：`/libra/fbs`。
>
> 官方教程：[创建 FBS 仓并设置配送](https://www.youtube.com/watch?v=4XrzVbU5pww)，2024-09-19；[FBS 包装与交接](https://www.youtube.com/watch?v=SUgP3IKxL8M)，2024-10-29；官方时间轴/描述核验日期：2026-08-03。另参考 [2022 年 FBS 规则更新](https://seller.ozon.ru/media/news/fbs-izmeneniya-v-reglamente-s-11-aprelya-2022/)，仅作历史规则证据。

FBS 中商品保存在卖家自有仓；订单产生后由卖家拣货、包装、打印货件标签并在规定时间交给 Ozon，后续交付由 Ozon 物流完成。它与 FBO 最大差异不是菜单，而是订单发生前库存保管方和订单发生后的备货责任方。

### 稳定业务链

`seller_stock_available → order_created → awaiting_pack → packed → label_created → handed_to_ozon → in_ozon_delivery → delivered / cancelled / returned`

至少需要：

- 卖家仓、仓内实际/承诺库存、营业和备货日历；
- 配送方法、商品类型、交接方式、接收点/上门取件和覆盖区域；
- 备货截止、包装、货件标签、交接扫描和视频留证；
- 缺货、逾期备货、错标、拒收、取消和退货事件；
- FBS 专属佣金/物流/退货费用和服务指标。

官方教程提到可配置多个卖家仓、商品类型、交接方式、交接时间和覆盖区域；这些选项与当前可用性必须按后台实时核验。2022 公告中的单据份数、KGT 重量、仓点和验收数字不能作为现行规则。

### 项目边界

- ozon-workbench 不创建 FBS 仓、不上传自有仓库存、不处理 FBS 备货/交接、不打印 FBS 标签。
- 为识别历史或误入数据，只保留 `fulfillment_scheme=fbs`、仓、订单时间线、费用和异常的只读模型。
- 任何 FBS 订单必须从 FBO 看板和 KPI 中隔离；不得把卖家仓库存计入 Ozon 仓可售库存。

## 60. realFBS：卖家控制承运与逆向物流

> Ozon 大学入口：`/libra/rfbs`。
>
> 官方回放：[realFBS 销售与合作配送专题](https://www.youtube.com/watch?v=UOiVF_SbK50)，Ozon для партнёров，2023-02-03；官方时间轴核验日期：2026-08-03。补充历史公告：[realFBS Standard 修改配送日期](https://seller.ozon.ru/media/news/realfbs-standard-mozhete-sami-perenosit-daty-dostavki-zakazov/)、[调包/丢失补偿](https://seller.ozon.ru/media/news/realfbs-zakrepili-kompensacii-za-podmenu-i-propazhu-tovara/)。

官方专场覆盖 realFBS 特点、质量控制、不同承运商、高峰期、KGT 多箱、退货/逆向流和 Express。稳定边界是：卖家不但保存和备货，还选择/管理自有或合作配送，并承担更完整的承运配置、时效回传和退货链路。

### 数据模型

- 配送方法/服务等级：Standard、Express 等按当期平台定义版本化；
- 承运商、合同、运单、包裹/多箱关系、路线和预计/实际时间；
- 卖家备货、承运商接收、干线、末端、交付尝试、改期和失败原因；
- 买家同意的日期变更、操作者、次数和对服务指标的影响；
- 退货标签、承运商逆向事件、收到/检查、调包/丢失/缺件与补偿案件。

2022/2023 公告中的改期次数、最大天数和补偿百分比只代表当时规则。当前规则必须核对 realFBS 正文和合同。

### 项目边界

- 项目不提供 realFBS 仓库、配送方式、承运商、改期、Express、KGT 多箱或退货操作能力。
- 只在统一订单层保存 `fulfillment_scheme=realfbs`，并隔离其服务指标和费用。
- 不把承运商扫描当作 Ozon 仓库事件，也不把 realFBS 退货规则套到 FBO。

## 61. 官方视频补充：销售模式识别与 FBO 库存迁移

> 官方来源：[Ozon 销售模式](https://www.youtube.com/watch?v=tDvsHlR_d_A)、[FBO 库存迁移](https://www.youtube.com/watch?v=E8LbsGKQF8k)，Ozon для партнёров；官方 RSS 标题与描述核验日期：2026-08-03。当前完成描述级核验，未取得完整字幕/时间轴。

销售模式视频再次确认 FBO、FBS、realFBS 的根本差异在商品存放、备货/发货责任和配送责任。项目路由必须以订单/库存事实中的履约模式为准，不能通过店铺、商品或历史默认值猜测；本项目只提供 FBO 写操作。

FBO 库存迁移是商品卡迁移的一部分，用于把符合条件的 Ozon 仓库存转移到另一个卖家后台。官方描述明确其涉及不可迁移库存、迁移所需合同和申请状态查询。结合已逐页核验的商品卡迁移正文，项目控制要求为：

- 把商品卡资产迁移、FBO 库存迁移和历史订单/财务归属拆成不同状态，不使用一个 `migrated=true` 覆盖全过程。
- 申请前快照源/目标法律主体与后台、商品卡 ID、offer/SKU、仓/集群、批次、可售/不可售数量、库龄、标记/序列证据和未清限制。
- 检查双方合同、权利与授权、贷款/保证金/争议、不可迁商品和需先取回的库存；具体清单以当前正文与后台校验为准。
- 保存申请 ID、创建人、审批证据、状态历史、逐 SKU 决定、部分成功、失败原因及迁移前后库存守恒核对。
- 迁移可能改变后续销售和库存归属，但不得改写迁移前订单、供货、仓储费、退货和财务事实的原始主体。
- 该流程默认只读监控和人工审批；项目不得自动签约、创建/撤销迁移申请或确认跨主体资产转移。
