# Ozon Seller API 蒸馏：面向 ozon-workbench

> 来源：[Ozon Seller API 官方文档](https://docs.ozon.ru/api/seller/)（文档标识 2.1）
>
> 核对日期：2026-07-30。官方页面当日识别到约 **487 个唯一接口**。本文是能力地图与工程决策摘要，不是接口字段镜像。

## 一句话结论

Seller API 足够把本项目从“本地经营看板”升级成“经营控制台”，但正确顺序应是：

1. 先稳住财务、FBO 订单、商品、价格、Ozon 仓库存五条只读数据链；
2. 再补 FBO 供应、退货、仓储费、评级、评价、搜索分析；
3. 最后才考虑改价、促销等少量写操作。

对当前项目最有价值的不是把 487 个接口全接上，而是围绕 FBO 建立可靠的领域模型、增量同步、版本治理和可解释对账。

## 0. 已确认范围：只做 FBO

本项目不做 FBS、rFBS、FBP。相关接口不进入产品路线和默认同步任务。

保留它们在本文中的唯一原因，是帮助识别官方文档、历史记录或财务流水里的履约模式，防止把非 FBO 数据错误归入 FBO。

项目应聚焦：

- FBO 商品与 Ozon SKU 主数据；
- FBO 订单和状态；
- FBO 仓库存、在途、预留和周转；
- FBO 供应草稿、供应单、货件和入仓结果；
- FBO 退货、补偿和报损；
- FBO 仓储、物流、佣金与其他服务费；
- FBO 补货、毛利和经营分析。

## 1. 基础规则

### 1.1 认证

- 基础地址：`https://api-seller.ozon.ru`
- 私有 Seller API 常用请求头：
  - `Client-Id`
  - `Api-Key`
  - `Content-Type: application/json`
- `/v1/roles` 用于检查当前密钥可访问的角色和方法，适合做“权限体检”。
- 公共或私有应用还可能使用 OAuth；单店本地工具优先使用最小权限 API Key。
- 密钥泄露时应立即撤销并轮换，不能只在应用中覆盖旧值。

### 1.2 请求与可靠性

- 大多数接口为 JSON `POST`，但存在 `GET`，不能按路径习惯猜方法。
- `401/403`：认证、角色、订阅或店铺状态问题。
- `429`：限流。应指数退避并加入抖动，避免所有任务同时重试。
- `5xx`：可重试，但写操作必须考虑幂等性，不能盲目重放。
- 每个接口的分页机制不同：常见有 `cursor`、`last_id`、`offset`、`page/page_size`。
- 时间通常为 ISO 8601；边界、时区和最大查询跨度必须按方法单独处理。
- 不应把“空结果”一律视为成功；它也可能代表无权限、筛选条件错误或数据尚未生成。

### 1.3 推荐的同步元数据

每次同步至少记录：

- `shop_id`
- `endpoint`
- `requested_from` / `requested_to`
- `started_at` / `finished_at`
- `cursor_or_page`
- `row_count`
- `http_status`
- `api_request_id`（若响应提供）
- `schema_version`
- `is_complete`
- `error_category`

这样才能回答“页面没数据，是店铺确实没有，还是同步没拉完”。

## 3. 按业务域蒸馏

### 3.1 商品、类目与内容

核心流程：

1. 获取类目树；
2. 获取类目属性及可选值；
3. 创建或更新商品；
4. 轮询导入任务；
5. 查询商品列表和详情；
6. 补图片、证书、价格和库存。

当前官方能力中最值得关注的路径：

- `/v1/description-category/tree`
- `/v1/description-category/attribute`
- `/v1/description-category/attribute/values`
- `/v3/product/import`
- `/v1/product/import/info`
- `/v3/product/list`
- `/v3/product/info/list`
- `/v4/product/info/attributes`
- `/v1/product/info/description`
- `/v1/product/pictures/import`
- `/v2/product/pictures/info`
- `/v1/product/archive`、`/v1/product/unarchive`

工程要点：

- `offer_id` 是卖家自己的稳定货号；`product_id` 和 `sku` 是平台标识，三者不要混用。
- 商品导入通常是异步任务：“请求接受”不等于“商品已发布”。
- 类目属性会变化，必须缓存并带更新时间，不能长期硬编码。
- 图片、描述、属性、价格、库存是不同数据面，需分别建同步状态。
- 归档比删除更适合运营工具；删除属于高风险动作。

对项目的直接价值：

- 建立统一 SKU 主数据；
- 修复图片和名称缺失；
- 展示商品内容完整度和被拒原因；
- 将价格、库存、订单、费用全部落到同一个 `offer_id/product_id/sku` 映射层。

### 3.2 价格、库存和定价策略

核心路径：

- `/v1/product/import/prices`
- `/v5/product/info/prices`
- `/v2/products/stocks`
- `/v4/product/info/stocks`
- `/v2/product/info/stocks-by-warehouse/fbs`
- `/v1/pricing-strategy/*`

必须区分：

- 当前售价、原价、促销价；
- FBO 可售、预留量、在途量和 Ozon 仓分布；
- 平台活动价与卖家定价策略；
- 展示价格与财务实际结算金额。

建议：

- 当前项目先只读，生成“建议价/补货建议”，不要自动提交。
- FBO 库存由 Ozon 仓储履约产生，本项目不建设 FBS 库存写入。
- 价格变更必须有上下限、毛利保护、审批、审计和回滚记录。

### 3.3 订单与履约

本项目只采用 FBO：货在 Ozon 仓，Ozon 承担仓储和主要履约；项目重点是订单结果、供应入仓、库存、退货和财务。

读取订单的关键路径：

- `/v2/posting/fbo/list`
- `/v2/posting/fbo/get`
- FBS/rFBS/FBP 订单接口不接入。

工程要点：

- `posting_number` 是履约单标识，不必然等于买家订单或财务流水的唯一键。
- 状态是生命周期，不应只保存最终状态；建议保存状态快照或事件。
- 同一订单可能拆成多个 posting；一条财务操作也可能包含多个服务费子项。
- 写履约状态会产生真实外部后果，当前看板不应默认开放。

### 3.4 FBO 供应、货件和 Ozon 仓

主要能力：

- FBO 可用仓库和入仓方向；
- FBO 供应草稿、供应单、货件和箱唛；
- 运输批次、装载、交接文档和状态；
- 到仓、验收、差异、上架和可售结果。

代表路径：

- `/v1/warehouse/fbo/list`
- `/v1/warehouse/fbo/seller/list`
- `/v1/draft/*`
- `/v1/supply-order/*`
- `/v1/cargoes/*`
- `/v1/carriage/*`

`/v1/warehouse/fbs/*`、`/v1/warehouse/erfbs/*` 和 FBP 端点均不接入。

对项目的价值：

- 把库存周转从“总量”升级到“Ozon 仓 × SKU × 可售状态”；
- 建立供应计划、缺货风险和在途可视化；
- 解释仓储费和长期仓储费；
- 将订单缺货、取消与具体仓库关联。

### 3.5 退货、取消与售后

核心能力：

- 汇总退货列表；
- FBO 退货和返还；
- 退货交付、条码、返还批次；
- 取消原因、条件取消和取消申请。

代表路径：

- `/v1/returns/list`
- `/v1/return/*`
- `/v1/conditional-cancellation/*`
- `/v2/posting/fbs/cancel-reason/list`

工程要点：

- 退货不是简单负销售；退款、退货物流、补偿、损耗可能在不同时间入账。
- 应把“申请—运输—验收—退款—重新可售/报损”建成生命周期。
- 对账时不要用订单日硬配所有费用，应保留发生日、结算期和关联键。

### 3.6 财务、现金流与报告

核心路径：

- `/v3/finance/transaction/list`
- `/v3/finance/transaction/totals`
- `/v1/finance/cash-flow-statement/list`
- `/v1/report/*`

财务模型应至少分开：

- 商品销售计提；
- 平台佣金；
- 履约与物流服务；
- 仓储与供应服务；
- 推广或订阅；
- 退款、退货、补偿和其他调整；
- 现金流/账单结算。

关键结论：

- 流水接口和现金流账单解决的是不同问题，不能互相冒充。
- 流水中的聚合操作需要拆出服务费子项，否则 SKU 毛利会失真。
- 无订单费用应进入独立费用池，而不是强行配到某个 posting。
- 异步报告适合补充明细和做周期性快照，但必须记录报告参数、生成时间和文件校验值。
- “平台应结”“银行实收”“经营利润”是三个不同口径。

### 3.7 分析、搜索和周转

代表能力：

- 销售分析；
- 仓库库存分析；
- 库存周转；
- 商品搜索词及详情；
- 搜索查询汇总。

注意：

- 部分分析指标需要 Premium/Premium Plus 或特定角色。
- 无订阅导致的失败应降级，不能阻断订单和财务核心同步。
- 分析接口常是聚合数据，不能用来替代订单/财务事实表。

对项目最有帮助的衍生指标：

- 销售额、件数、客单、退款率；
- 可售天数、缺货天数、滞销天数；
- 搜索曝光→点击→加购→下单漏斗；
- 广告/促销前后毛利变化；
- SKU × 仓库的补货建议。

### 3.8 促销与卖家活动

三类能力：

- Ozon 平台活动：`/v1/actions/*`
- 卖家自建活动：`/v1/seller-actions/*`
- 定价策略：`/v1/pricing-strategy/*`

项目应用：

- 展示商品是否参加活动、活动价和时间范围；
- 将活动折扣纳入毛利模拟；
- 找出“销售上涨但利润下降”的活动；
- 自动生成候选清单，但暂不自动报名或改价。

### 3.9 评级、评价、问答与聊天

能力域：

- `/v1/rating/*`
- `/v2/review/*`
- `/v1/question/*`
- `/v1/chat/*`

可以形成：

- 店铺健康度和评级趋势；
- SKU 差评主题；
- 未回复评价/问题/会话；
- 取消、迟发、质量问题与差评的关联分析。

聊天和回复属于外部通信。即使技术上可写，也必须保留人工确认。

## 5. 需要优先复核的代码风险

### P0：旧类目路径

代码使用：

- `/v1/category/tree`
- `/v1/category/attribute`

当前官方能力地图展示：

- `/v1/description-category/tree`
- `/v1/description-category/attribute`
- `/v1/description-category/attribute/values`

应以当前方法页为准迁移，并补充响应结构测试。旧路径可能已下线或仅对部分账户兼容。

### P0：重试不是完整的限流策略

当前客户端对 `429/502/503/504` 做固定递增等待。建议改为：

- 指数退避 + 随机抖动；
- 尊重 `Retry-After`（若有）；
- 店铺级与端点级限流；
- 同步任务可续跑；
- 写操作单独的幂等与重试规则。

### P0：分页完成度

多处使用固定 `pages < 50` 保护。如果大店超过上限，会静默得到不完整数据。应：

- 保存 cursor；
- 标记 `is_complete=false`；
- 暴露“截断”告警；
- 支持续跑而不是把 50 页当作成功。

### P1：`/v1/roles` 的方法

代码先 POST、异常后 GET。应从当前官方方法定义确认唯一 HTTP 方法；不能把所有异常都当作“方法不对”，否则会掩盖认证、限流或服务异常。

### P1：接口返回结构兼容

代码有多处 `data.get("items") or data.get("result", {}).get("items")`。这适合过渡，但会隐藏版本漂移。建议为每个端点定义明确响应适配器和契约样本。

### P1：时间边界

财务按 28 天切片是实用保护，但 `chunk_start = chunk_end + 1 秒` 需要通过边界测试确认既不重不漏。最佳方案是：

- 原始数据按平台唯一键幂等 upsert；
- 查询窗口允许小范围重叠；
- 存储 UTC，展示时再转店铺时区；
- 同步完成后做 totals/报表交叉校验。

### P2：乱码与可维护性

仓库中的部分中文源码和 README 呈现为乱码。它会妨碍接口维护和交接，建议统一 UTF-8，并在 CI 增加编码检查。

## 6. 推荐落地路线

### 第一批：可靠性（立刻做）

1. 建立端点注册表：路径、HTTP 方法、权限、分页、时间跨度、版本、读写风险。
2. 迁移 `description-category` 接口。
3. 为全部已接端点补契约测试和分页完成度。
4. 统一错误分类、限流、重试和同步元数据。
5. 在 UI 显示最后成功时间、数据区间、完整性和失败原因。

### 第二批：经营价值

1. SKU 主数据与三类标识映射。
2. 仓库 × SKU 库存、在途、预留、可售天数。
3. 退货全生命周期与退款/费用解释。
4. 评级、评论、搜索漏斗与商品健康度。
5. 活动价、费用和毛利模拟。

### 第三批：谨慎写入

只在具备审批、审计、幂等和回滚后考虑：

- 更新价格；
- 参加或退出活动；
- 回复评价、问答或聊天。

## 8. 对使用者最有帮助的认识

1. **销量不是利润。** 促销、佣金、物流、仓储、退货和无订单费用会改变真实结果。
2. **库存不是一个数。** 要看履约模式、仓库、预留、在途和可售状态。
3. **退货不是一笔负销售。** 它是跨时间的物流与财务生命周期。
4. **平台数据有多个时间轴。** 下单、发货、退货、计费、结算和到账不能只按一天对齐。
5. **API 是经营事实入口，不是最终答案。** 最终答案来自可解释的本地模型和交叉校验。
6. **自动化越靠近写操作，风险越高。** 先把建议做对，再把执行自动化。

## 9. 下一阶段学习方向

下一阶段应进入 Ozon 卖家知识库，而不是继续逐字段抄 API：

1. FBO 的真实业务规则、供应入仓与费用；
2. 订单、取消、退货和赔付规则；
3. 商品质量、搜索排序、促销和定价；
4. 结算、账单、服务费与仓储费；
5. 评级、评价和店铺风险指标。

这些内容能解释“API 字段为什么这样变化”，也是判断哪些功能真正值得加入项目的关键。

## 10. FBO 供应 API 的 2026 年兼容性约束

> 官方来源：Ozon for developers，〈Изменения в методах Seller API при работе с поставками FBO〉
>
> 发布：2026-01-19；生效：2026-02-16；核验：2026-07-30

仅对跨仓 FBO 供应：

- `/v3/supply-order/get` 与 `/v1/supply-order/details` 新增 `macrolocal_cluster_id`；
- `storage_warehouse.arrival_date` 永远返回 `null`；
- `warehouse_id` 对跨仓供应失去业务定位意义；
- 草稿计算、时隙查询和供应申请创建均转为集群维度。

工程上必须做到：

1. 解析器兼容 `warehouse_id` 为空或不再适用；
2. 把 `macrolocal_cluster_id` 保存为一等字段；
3. 通过供应路线类型决定使用集群还是仓库，不能用非空字段猜测；
4. 不以 `storage_warehouse.arrival_date` 计算 SLA；
5. 为 2026-02-16 前后的响应保存契约样本；
6. 对新增枚举和未知字段采用可追溯的向前兼容策略；
7. 在 API 注册表记录规则生效日期和官方变更来源。

此外，Ozon 官方开发者社区对 `/v1/draft/supply/create` 的案例说明：创建跨仓供应时，`warehouse_id` 指的是存储仓标识，不能与发运仓混用；相应标识应从草稿信息接口返回的数据中取得。错误映射可能触发 `INVALID_STORAGE_WAREHOUSE`。该案例属于旧接口时期的故障解释，实施新流程时仍须以当前 Seller API 方法页为准。

## 11. 2026-06 至 2026-07 的 FBO API 变更

> 官方来源：Ozon Seller API notification；核验日期：2026-07-30。

### 供应申请新版方法

Ozon 在 2026-06-01 公告：

- 新增 `/v2/draft/supply/create`；
- 更新 `/v1/draft/crossdock/create`；
- 更新 `/v1/draft/direct/create`；
- 更新 `/v1/draft/multi-cluster/create`；
- `/v2/cluster/list` 从 Beta 转入主文档；
- 官方 FBO“创建供应申请”方法工作流同步更新。

项目接入供应申请时，应从路线类型开始分流：

1. 直接供应：`direct`；
2. 跨仓供应：`crossdock`；
3. 多集群供应：`multi-cluster`；
4. 查询异步草稿结果和时隙；
5. 使用 v2 方法从草稿创建正式供应申请；
6. 轮询创建状态，不能把 HTTP 成功视为申请已经建成。

正式实施前仍需逐个核对当前方法页的请求体、权限、异步状态和错误枚举。

### 新增 FBO 仓库存方法

Ozon 在 2026-06-02 公告新增：

- `/v1/product/info/stocks-by-warehouse/fbo`：按 FBO 仓库获取库存信息。

2026-08-11 使用真实 Ozon 店铺完成只读契约验证：

- HTTP 方法：`POST`；
- 请求必须包含 `skus` 或 `offer_ids`，字段名是复数；
- 请求分页字段：`limit`（1–1000）与可选 `cursor`；
- 响应顶层字段：`products`、`has_next`、`cursor`；
- `products` 行已确认包含 `sku`、`offer_id`、`product_id`、`warehouse_id`、`present`、`reserved`；
- 单个 SKU 会返回多个 FBO `warehouse_id`，包括数量为 0 的仓库行；
- 当前响应不直接提供仓库名称，因此仍需仓库主数据映射或与带仓名来源并行使用。

真实双店影子核对发现，新方法与 `/v2/analytics/stock_on_warehouses` 在部分货号的即时总量不一致。可能原因包括刷新频率与库存口径差异；在逐项解释完成前，不得直接替换生产库存来源。

该方法应作为当前仓库库存链的候选主来源，并与现有：

- `/v4/product/info/stocks`；
- `/v2/analytics/stock_on_warehouses`；
- `/v1/analytics/turnover/stocks`

做字段、粒度、延迟和总量交叉验证，不能未经验证直接替换。

### FBO 订单列表强制迁移

Ozon 在 2026-07-10 公告：

- `/v2/posting/fbo/list` 已进入弃用期；
- 计划于 **2026-08-31** 停用；
- 必须迁移到 `/v3/posting/fbo/list`。

ozon-workbench 当前 `backend/app/ozon_client.py` 仍调用 v2，因此这是 **P0 兼容性风险**。

迁移验收：

- 使用 v3 单独实现，不在原函数中静默改解析；
- 保存 v2/v3 脱敏契约样本；
- 同一时间窗口并行对比订单数、posting 数、SKU 数量和金额；
- 核对状态过滤、时间字段、分页与取消订单口径；
- 处理 v3 新增字段和未知枚举；
- 对比通过后再切换读路径；
- 在 2026-08-31 前删除对 v2 的生产依赖。

### 运输货件分配

Ozon 在 2026-07-09 公告，Seller API 的 FBO 工作流增加了“把商品分配到运输货件”的说明。

这意味着供应自动化不能只创建供应申请，还必须建立：

`供应申请 → 运输货件 → 箱/托盘 → SKU 与数量`

项目必须保存货件组成提交状态、异步处理状态、平台返回错误和最终货件组成；否则无法可靠解释验收差异与附加服务费。
